# Permission Rules

## 1. 세션 관리자는 항상 한 명이다

`hostUserId`는 호환을 위해 유지하는 내부 이름이며, 실제 의미는 세션 관리자 ID다. 세션 생성자가 관리자가 되고 별도 관리자 이전은 지원하지 않는다.

지켜야 할 것:

- 사람 GM 세션에서는 세션 관리자와 GM이 항상 같은 사용자다.
- AI GM 세션에서는 세션 관리자가 일정·모집·설정을 담당하고 AI가 GM을 맡는다.
- 사람 GM을 다른 참가자로 지정하거나 교체하는 API와 UI를 제공하지 않는다.
- 세션 설정, 일정, 참가 승인, 구성원 관리와 삭제 권한은 `hostUserId` 하나로 판단한다.
- `ParticipantRole.GM`과 `ParticipantRole.HOST`는 별도 권한 원천이 아니라 현재 `gmMode`에서 파생되는 관리자 표시 역할이다.

이유:

세션 생성에는 시나리오 선택과 접근 권한이 필요하고, 개인 시나리오는 일반적으로 GM이 소유한다. 사람 GM과 관리자를 분리하면 실제 사용 흐름보다 권한 원천만 늘어나며 서로 다른 사용자를 가리키는 `hostUserId`, `gmUserId`, participant role 사이에 모순이 생긴다.

## 2. GM 모드 전환은 관리자의 역할만 바꾼다

모든 세션은 `gmMode = AI | HUMAN`을 가진다.

지켜야 할 것:

- `AI → HUMAN` 전환 시 현재 세션 관리자가 GM이 된다.
- `HUMAN → AI` 전환 시 기존 GM은 세션 관리자로 남고 AI가 GM 역할을 넘겨받는다.
- 모드 전환은 방 설정을 수정할 수 있는 `DORMANT`와 `LOBBY_OPEN`에서만 허용한다.
- 사람 GM으로 전환하면 관리자의 플레이어 캐릭터 연결과 준비 상태를 정리한다.
- AI GM으로 전환하면 관리자의 참가자 역할은 `HOST`, 사람 GM으로 전환하면 `GM`으로 바꾼다.
- 호환 필드 `gmUserId`는 사람 GM이면 `hostUserId`, AI GM이면 `null`로만 저장하고 응답한다. 권한 판단에는 사용하지 않는다.

이유:

GM 모드는 진행 주체를 선택하는 설정이지 다른 사용자에게 운영권을 넘기는 기능이 아니다. 관리자 동일성을 유지해야 일정·시나리오·모집·플레이 제어 권한이 한 사용자에게 일관되게 남는다.

## 3. 사람 GM 기능은 모드와 관리자 권한을 함께 확인한다

지켜야 할 것:

- 사람 GM 전용 패널과 API는 `gmMode = HUMAN`일 때만 활성화한다.
- 사람 GM 전용 API는 요청 사용자가 `hostUserId`와 같은지도 확인한다.
- AI GM 세션의 관리자는 방을 관리하지만 사람 GM 전용 노드 이동, 자료 공개, NPC 대사, 직접 전투 제어 권한을 받지 않는다.
- UI 조건과 백엔드 권한 조건은 같은 의미를 가져야 한다.

이유:

관리자가 GM을 겸하는 것은 사람 GM 모드에 한정된다. AI GM 세션에서 관리 권한과 사람 GM 런타임 권한을 섞으면 AI 진행과 수동 진행이 충돌한다.

## 4. 플레이어 권한과 세션 운영 권한을 분리한다

플레이어는 자신의 캐릭터 행동, 채팅, 주사위 굴림을 수행한다. 세션 관리자는 일정, 모집, 설정과 모드에 따른 GM 기능을 수행한다.

지켜야 할 것:

- 캐릭터 조작은 세션 참가자와 세션 캐릭터 연결을 기준으로 확인한다.
- 전투 중 행동은 현재 턴과 액션 자원을 확인한다.
- 노드 변경, 자료 공개, NPC 대사 직접 전송, 전투 시작은 사람 GM 모드의 세션 관리자로 제한한다.
- 세션 모집·일정·구성원 관리 기능은 GM 모드와 관계없이 세션 관리자로 제한한다.

## 5. Projection은 대상 권한에 맞춰 나간다

같은 원본 데이터라도 플레이어, AI GM 세션 관리자, 사람 GM에게 보여줄 수 있는 필드는 다르다.

지켜야 할 것:

- GM 메모, 비공개 단서, 숨겨진 전이 조건은 플레이어 응답에 포함하지 않는다.
- 공개된 단서는 `SessionReveal` 기준으로 보여준다.
- 세션 노드의 `checkOptionsJson`, `cluesJson`, `transitionsJson`은 응답 대상에 맞춰 필터링한다.
- 프론트가 숨겨야 할 정보를 받은 뒤 UI에서만 감추는 방식은 피한다.

이유:

TRPG 시나리오에는 플레이어에게 공개되면 안 되는 정보가 많다. 권한 projection을 서버에서 처리해야 비공개 정보 노출을 막을 수 있다.
