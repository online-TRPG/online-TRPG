## 1. 결론

현재 프로젝트는 캐릭터 생성·성장, AI/사람 GM, 판정·전투·VTT, 실시간 로그, 시나리오 제작처럼 실제 TRPG를 진행하기 위한 코어 기능이 넓게 구현되어 있다. 그러나 사용자가 처음 방문해 세션을 찾고, 원활하게 참가하고, 다음 방문에서 이어서 플레이하는 제품 흐름은 공개 베타 기준에 미치지 못한다.

따라서 다음 개발 사이클에서는 룰과 콘텐츠의 폭을 더 넓히기보다 아래 다섯 결과를 먼저 달성한다.

1. 처음 온 사용자가 튜토리얼을 완료하거나 건너뛰고 기존 세션 흐름으로 진입한다.
2. 공개 세션이 10개를 넘어도 검색·필터·페이지 이동 결과가 누락되지 않는다.
3. 방장이 공개/비공개 세션을 만들고 수정한 뒤 실제 링크로 초대할 수 있다.
4. 공개 세션의 설명을 충분히 확인하고 참가하며, 참가자는 자유롭게 탈퇴하고 방장은 문제 사용자를 내보낼 수 있다.
5. 여러 세션에 소속된 사용자가 플레이 일정을 조율하고, 같은 시각에는 하나의 실시간 세션에만 참여한다.

공개 베타는 P0 항목과 UX-10의 핵심 접근성 범위가 모두 완료된 뒤에만 시작한다. P0이 끝나기 전 외부 사용자를 받는 경우에는 초대 기반 비공개 알파로 한정한다.

## 2. 계획의 전제와 범위

### 전제

- 웹 플랫폼과 현재 AI/사람 GM 이중 구조를 유지한다.
- 게임 상태의 최종 권위는 기존처럼 규칙 엔진과 상태 엔진에 둔다.
- 일정은 팀 인원과 가용 시간이 정해지지 않았으므로 달력 대신 `S/M/L/XL` 상대 크기로 표기한다.
- 공개 세션에서 서로 모르는 사용자가 만나는 상황을 제품 범위로 본다.
- 이 문서는 2026-07-11 코드 정적 점검 결과를 기준으로 작성했다. 문서 작성 과정에서 테스트나 브라우저 수동 검증은 실행하지 않았다.

### 포함 범위

- 최초 방문 튜토리얼과 기존 세션 흐름 안내
- 홈의 이어하기, 플레이 일정, 시작 시간 근접 경고, 단일 실시간 참여
- 세션 검색, 필터, 페이지네이션, 정확한 전체 개수
- 세션 생성·수정·일정·공개 범위·초대 링크
- 시나리오 메타데이터와 제공 콘텐츠 큐레이션
- 공개 세션 설명, 참가자 탈퇴, 방장 내보내기
- 사람 GM과 시나리오 제작자의 기본 편집 흐름
- 사용자용 문구, 내부 ID 제거, 데스크톱 웹 접근성
- 계정 복구, OAuth 계정 탈퇴, 게스트 보존 안내
- 사용자 여정 기반 계측과 공개 베타 검증

### 제외 범위

- 신규 룰셋, 클래스, 주문, 몬스터의 대규모 추가
- 모바일 웹과 네이티브 모바일 앱
- 유료 콘텐츠 마켓과 결제
- 사용자 간 자유 형식 DM
- 평점 기반 GM/플레이어 서열화
- 운영 배포, 운영 DB 변경, 외부 분석 서비스 계약

## 5. 공통 제품 결정

다음 결정은 개별 구현에서 다시 다르게 해석하지 않는다.

- 목록 검색·필터·정렬·페이지 계산은 서버가 수행한다. 프론트는 서버가 반환한 한 페이지를 다시 전체 목록처럼 필터하지 않는다.
- 초대 링크를 여는 동작만으로 세션 참가 상태를 변경하지 않는다. 제한된 미리보기를 보여 준 뒤 사용자가 참가를 확정한다.
- `maxParticipants`는 호환성을 위해 현재와 같이 호스트/사람 GM을 포함한 총 참여 인원으로 유지한다. 화면에는 반드시 `총 인원(GM/호스트 포함)`이라고 표시한다.
- 사용자는 여러 세션에 소속되거나 여러 공개 세션에 참가 신청할 수 있다. 세션 소속, 특정 플레이 일정 참석, 실시간 대기실·플레이 참여는 서로 다른 상태로 관리한다.
- 예약 전후에는 `플레이 일정`, 진행 중에는 `현재 플레이`, 기록에서는 `지난 플레이`로 표현하고, 내부 데이터 모델은 `SessionPlay`로 통일한다.
- 플레이 일정에는 시작 시각만 필수로 받고 종료 시각은 요구하지 않는다. 새 플레이 시작이 기존 신청·참석 일정과 6시간 이하로 가까우면 경고하되 참가나 일정 확정을 차단하지 않는다.
- 한 사용자가 실시간으로 점유할 수 있는 대기실·플레이는 모든 탭과 기기를 합쳐 하나다. 다른 플레이로 이동할 때는 사용자의 확인 후 이전 실시간 점유를 해제하고 새 플레이를 원자적으로 점유한다.
- 시나리오 메타데이터가 없으면 `미정` 또는 항목 미표시를 사용한다. 제목이나 난이도로 플레이 시간·테마·입문자 적합성을 추측하지 않는다.
- 세션과 시나리오의 소재·분위기를 설명할 책임은 방장과 작성자에게 둔다. 플랫폼은 자유 형식 설명을 잘 작성하고 읽을 수 있게 하되 소재 적합성을 분류·보증하거나 확인을 강제하지 않는다.
- 공개 세션의 기본 운영은 참가자의 자발적 세션 탈퇴와 방장의 참가자 내보내기·재초대에 한정한다.
- 사용자 화면에는 내부 ID, 저장용 key, raw enum을 표시하지 않는다. URL에 public ID가 필요하더라도 본문에는 렌더링하지 않는다.
- 자유 형식 DM은 이번 계획에 포함하지 않는다. 모집 전 조율은 세션 참가 메모로 제한한다.
- 계측 이벤트에는 행동 원문, 채팅 원문, AI 프롬프트를 넣지 않는다.

## 6. 세부 구현 계획

## UX-01. 서버 기준 세션 탐색

### 사용자 결과

- 11번째 이후 세션도 검색과 페이지 이동으로 찾을 수 있다.
- 공개 세션 수와 내 세션 수가 실제 전체 개수와 같다.
- 검색어, GM 유형, 상태, 시나리오, 일정, 정렬을 바꾸면 서버 기준 결과가 일관되게 갱신된다.

### 구현 작업

1. `shared-types/src/dto/api/sessions.dto.ts`
   - `SessionListQueryDto`에 `query`, `gmMode`, `sort`를 추가한다.
   - `sort`는 우선 `recent`, `soonest`, `title`만 허용한다.
   - `page`, `size`, 필터의 최대 길이와 허용 값을 DTO에서 검증한다.
2. `be/src/modules/sessions/sessions.controller.ts`, `be/src/modules/sessions/sessions.service.ts`
   - 제목·설명·시나리오 제목 검색과 GM/상태 필터를 DB `where`에 반영한다.
   - 정렬에는 항상 안정적인 ID tie-breaker를 둔다.
   - `PUBLIC` 목록과 `내 세션`의 권한 조건을 별도 query builder로 유지한다.
3. `fe/src/services/sessionApi.ts`
   - `listSessions(params)`와 `listMySessions(params)`가 query를 직렬화한다.
   - 응답의 `content`, `page`, `totalElements`, `totalPages`를 모두 보존한다.
4. `fe/src/hooks/useSession.ts`
   - 목록 상태를 플레이 실시간 상태와 분리한 `useSessionCatalog` 후보 hook으로 이동한다.
   - 공개/내 세션의 페이지와 필터 상태를 별도로 관리한다.
   - 이전 요청보다 늦게 끝난 응답이 최신 화면을 덮지 않도록 요청 sequence 또는 `AbortController`를 사용한다.
5. `fe/src/pages/SessionDiscoverPage.tsx`, `fe/src/pages/LobbyPage.tsx`
   - 로컬 전체 목록 필터와 `slice()` 기반 페이지네이션을 제거한다.
   - 검색 입력은 250~400ms debounce 후 요청한다.
   - 페이지 번호, 전체 결과 수, 로딩, 결과 없음, 재시도 상태를 구분한다.

### 실패 처리

- 마지막 페이지에서 세션이 삭제되어 빈 페이지가 되면 유효한 마지막 페이지로 한 번만 재요청한다.
- 필터 요청 실패 시 기존 결과를 즉시 지우지 않고 오류와 재시도 버튼을 함께 보여 준다.
- 잘못된 page/size/sort는 400으로 거절하며 임의 보정하지 않는다.

### 완료 조건

- 공개 세션 12개를 만들었을 때 11번째와 12번째가 검색 및 페이지 이동으로 노출된다.
- 필터 적용 후 `totalElements`와 실제 반환 가능한 ID 집합이 일치한다.
- 홈 카운트가 현재 페이지 길이가 아니라 서버 전체 개수를 표시한다.
- 빠르게 검색어를 바꿔도 오래된 응답이 최신 결과를 덮지 않는다.

## UX-02. 세션 생성·수정·초대 완성

### 사용자 결과

- 방장은 제목, 설명, 시나리오, GM 유형, 총 인원 1~8명, 공개 범위, 다음 일정을 설정한다.

### 권한과 실패 처리

- 방 설정 변경은 호스트만 가능하며 `DORMANT`와 `LOBBY_OPEN`에서 허용한다.
- 제목, 설명, 시나리오, GM 유형, 공개 범위, 총 인원 등 방 설정 전체를 `PLAYING`, `COMPLETED`, `DISBANDED`에서는 변경할 수 없다. 서버도 같은 상태 규칙으로 수정 요청을 거절한다.
- 현재 참가 인원보다 작은 정원으로 낮출 수 없다.
- 플레이 일정 예약·변경·취소, `진행 저장 후 닫기`, 참가자 관리는 방 설정 변경과 구분하고 각 기능의 상태·권한 규칙을 따른다.
- 만료·회전·오타 코드에는 세션 존재 여부를 과도하게 노출하지 않는 동일한 사용자 메시지를 사용한다.
- 링크 미리보기는 참가자 목록, 로그, 비공개 노트, 내부 ID를 반환하지 않는다.

### 완료 조건

- 공개/비공개 세션을 각각 만들고 새로고침 후 모든 입력값이 유지된다.
- 생성한 세션을 수정하면 목록·상세·플레이 설정에 같은 값이 보인다.
- `PLAYING`에서는 방 설정 수정이 UI와 API 모두 거절되고, `진행 저장 후 닫기` 후 `DORMANT`에서는 다시 수정할 수 있다.
- 로그아웃 상태에서 초대 링크를 연 뒤 로그인해도 같은 초대 흐름으로 복귀한다.
- 링크를 열기만 해서는 참가자가 추가되지 않는다.
- 링크 복사 결과를 새 브라우저에 붙여 넣어 참가까지 완료할 수 있다.

## UX-03. 최초 방문 튜토리얼과 이어하기

### 사용자 결과

- 처음 온 사용자는 최초 진입 시 기존 캐릭터·세션 생성과 플레이 흐름을 설명하는 짧은 튜토리얼을 제공받는다.
- 튜토리얼은 기존 세션 생성에서 AI GM과 1인 구성을 선택하도록 안내할 뿐, 별도 체험 세션이나 전용 진입 버튼을 만들지 않는다.
- 홈에는 `이어하기`가 가장 먼저 보이고, 현재 장면·마지막 활동·다음 일정이 함께 표시된다.
- 온보딩은 강제 장문 튜토리얼이 아니라 실제 플레이 안에서 필요한 순간에만 나타난다.

### 구현 작업

1. 최초 방문 튜토리얼
   - 첫 로그인 후 메인 진입 시 튜토리얼을 한 번 제안하고 `시작`과 `건너뛰기`를 제공한다.
   - 튜토리얼은 기존 캐릭터 생성 → 세션 생성 → AI GM 선택 → 1인 구성 → 첫 행동 흐름에서 현재 단계에 필요한 설명만 보여 준다.
   - 세션과 캐릭터는 기존 생성 API로 만들며 튜토리얼 전용 `quickstart` API, 자동 프리셋 캐릭터, 별도 체험 세션을 추가하지 않는다.
   - 홈이나 상단 메뉴에 `AI GM 체험`, `빠른 시작`, 중복 `세션 찾기` 버튼을 추가하지 않는다.
2. 온보딩 진행 상태
   - 신규 후보 `UserProductProgress`에 `onboardingVersion`, `tutorialStartedAt`, `firstActionAt`, `completedAt`, `dismissedAt`, `dismissedCoachmarks`를 저장한다.
   - 브라우저 저장소는 화면 표시 캐시로만 쓰고 서버 값을 기준으로 한다.
3. `fe/src/pages/LobbyPage.tsx`
   - 진행 중 세션이 있으면 최근 활동 기준 `이어하기` 카드를 첫 행동으로 배치한다.
   - 최초 방문 튜토리얼 외에는 기존 상단 탭과 공개 세션·내 세션·세션 생성 진입을 그대로 사용한다.
   - 게스트에게는 튜토리얼 시작 전에 7일 보존 정책과 회원 전환 이점을 짧게 알린다.
4. `fe/src/pages/PlayPage.tsx`
   - 첫 플레이에서 세 코치마크만 제공한다: 행동/채팅 구분, 판정 결과 읽기, `/힌트`·`/요약` 사용.
   - 코치마크는 닫기·건너뛰기가 가능하고 다음 방문에 반복하지 않는다.

### 실패 처리

- 튜토리얼을 중단하거나 건너뛰어도 기존 캐릭터·세션 생성과 플레이 기능은 제한하지 않는다.
- AI 호출 실패 시 기존 fallback·재시도 동작을 그대로 사용한다.
- 저장된 이어하기 대상이 완료·해산됐으면 활성 목록에서 제거하고 완료 기록으로 안내한다.

### 완료 조건

- 신규 사용자가 최초 방문 튜토리얼을 시작하거나 즉시 건너뛸 수 있다.
- 튜토리얼이 기존 생성 화면을 안내하며 별도 세션·캐릭터·홈 진입 버튼을 만들지 않는다.
- 튜토리얼을 완료하거나 건너뛴 사용자는 다음 방문에 다시 강제로 보지 않는다.
- 새로고침 또는 다른 기기 로그인 후 홈에서 활성 세션을 다시 열 수 있다.
- 코치마크를 건너뛴 사용자는 다시 강제로 보지 않는다.

## UX-05. 공개 세션 설명과 기본 구성원 운영

### 사용자 결과

- 방장은 세션 설명에 진행 방식, 예상 분위기, 일정과 참가자가 미리 알아야 할 내용을 자유롭게 작성한다.
- 참가자는 공개 세션 상세와 초대 미리보기에서 설명을 읽고 참가 여부를 결정한다.
- 참가자는 플레이 화면에서 나가는 것과 세션 자체를 탈퇴하는 것을 구분해 선택한다.
- 방장은 진행을 방해하는 참가자를 세션에서 내보내 자동 재입장을 막고, 필요하면 나중에 명시적으로 다시 초대한다.

### 책임 범위

- 세션과 시나리오의 소재·분위기를 설명할 책임은 방장과 작성자에게 둔다.
- 플랫폼은 소재를 구조화해 분류하거나 적합성을 보증하지 않는다.
- 별도 콘텐츠 정책, 확인 checkbox, 개인별 소재 선호, 사용자 관계 필터는 만들지 않는다.
- AI 응답과 재시도는 기존 구현을 그대로 사용하며 이 개선 계획의 신규 범위로 다루지 않는다.
- 서비스가 담당하는 범위는 설명 표시, 본인의 탈퇴와 방장의 구성원 관리에 한정한다.

### 세션 설명

1. 입력
   - 기존 `Session.description`을 사용하고 별도 정책 모델을 추가하지 않는다.
   - 공개 세션 생성 화면에서 설명 입력을 눈에 잘 보이게 배치한다.
   - placeholder는 `진행 방식, 예상 분위기, 일정, 참가자가 미리 알아야 할 내용을 자유롭게 작성해주세요.`처럼 작성 목적만 안내한다.
   - 설명은 필수 입력으로 강제하지 않으며 비어 있으면 `등록된 설명이 없습니다.`라고 표시한다.
2. 표시
   - 세션 탐색 카드에는 설명 일부를 줄여서 보여 준다.
   - 세션 상세과 초대 미리보기에는 전체 설명과 다음 플레이 일정을 보여 준다.
   - 설명에 없는 분위기·난이도·적합성을 프론트가 임의로 추측하지 않는다.
3. 수정
   - 방장은 다른 방 설정과 마찬가지로 `DORMANT`와 `LOBBY_OPEN`에서 설명을 수정할 수 있다.
   - 수정 결과는 목록, 상세, 세션 홈에 같은 서버 응답을 기준으로 반영한다.

### 참가자의 플레이 화면 나가기와 세션 탈퇴

1. `플레이 화면 나가기`
   - 현재 대기실 또는 플레이 room 연결만 종료한다.
   - 세션 소속, 캐릭터, 로그 접근 권한은 유지한다.
   - UX-06의 `UserActivePlay` 점유만 해제한다.
2. `세션 탈퇴`
   - 세션 소속을 끝내는 별도 행동으로 제공한다.
   - 확인 dialog에서 캐릭터와 세션 기록의 처리 결과를 설명한다.
   - 기존 `DELETE /sessions/:id/leave`를 사용하고 `ParticipantStatus.LEFT`, 현재 실시간 점유 해제, 준비·참석 상태 정리를 한 transaction으로 처리한다.
   - 호스트는 직접 탈퇴할 수 없으며 방장 이전 또는 세션 종료를 사용한다.
3. 재참가
   - 자발적으로 탈퇴한 사용자의 재참가 허용 여부는 대상 세션의 모집 상태와 방장 승인 정책을 따른다.
   - 방장이 내보낸 `KICKED` 상태와 자발적 `LEFT` 상태를 같은 정책으로 처리하지 않는다.

### 방장의 세션에서 내보내기

1. 권한
   - 호스트 또는 명시적으로 구성원 관리 권한을 가진 사람 GM만 실행한다.
   - 호스트 자신은 내보낼 수 없다.
2. 처리
   - 참가자 카드의 `세션에서 내보내기`에서 대상 표시명과 결과를 확인한다.
   - 성공 시 `ParticipantStatus.KICKED`, 현재 room 퇴장, `UserActivePlay` 해제, 준비·참석 상태 정리를 한 transaction으로 처리한다.
   - 같은 세션의 공개 참가, 기존 초대 코드, 직접 참가 API를 통한 자동 재입장을 거절한다.
   - 방장이 `내보내기 취소`를 실행하거나 새 초대를 발급하면 `KICKED`를 해제하고 다시 참가할 수 있다.
3. 범위
   - 참가자의 발언이나 로그 일부를 숨기는 음소거 기능은 추가하지 않는다.
   - 다른 세션의 탐색·참가·초대에는 영향을 주지 않는다.
   - 계정 전체 제재나 다른 사용자와의 관계 필터로 확장하지 않는다.

### API와 구현 위치

1. 세션 설명
   - 기존 `CreateSessionDto.description`, `UpdateSessionDto.description`, `SessionResponseDto.description`을 그대로 사용한다.
   - `fe/src/pages/SessionCreatePage.tsx`, 세션 상세, 세션 홈에서 같은 값을 표시한다.
2. 플레이 화면 나가기
   - Socket room leave와 `UserActivePlay` 해제만 수행하는 별도 클라이언트 행동을 둔다.
3. 세션 탈퇴
   - 기존 `DELETE /sessions/:id/leave`의 사용자 결과와 상태 정리를 UX-06 플레이 모델에 맞춘다.
4. 세션에서 내보내기
   - 신규 후보 `DELETE /sessions/:id/participants/:participantPublicId`를 호스트 권한으로 제공한다.
   - 응답은 변경된 participant 상태와 실시간 점유 해제 결과를 반환한다.
   - 신규 후보 `POST /sessions/:id/participants/:participantPublicId/restore`는 호스트가 `KICKED` 상태를 해제하고 재초대를 허용한다.

### 실패 처리와 권한

- 참가 인원 변경, 탈퇴, 내보내기가 동시에 발생해도 participant status와 transaction으로 최종 상태를 하나만 남긴다.
- 권한 없는 내보내기와 호스트 자신을 대상으로 한 내보내기는 거절한다.
- `KICKED` 사용자가 방장의 복구 없이 기존 invite code로 재참가하지 못하도록 join policy에서 검사한다.
- 자발적 탈퇴와 내보내기의 사용자 메시지와 재참가 정책을 구분한다.

### 완료 조건

- 방장이 작성한 세션 설명이 생성·탐색·상세·초대 미리보기에서 같은 내용으로 표시된다.
- 설명이 없어도 공개 세션을 만들 수 있으며 플랫폼이 분위기나 소재를 임의 생성하지 않는다.
- 플레이 화면 나가기는 세션 소속을 유지하고 실시간 점유만 해제한다.
- 세션 탈퇴는 `LEFT`, 방장 내보내기는 `KICKED`로 구분된다.
- 방장이 사용자를 내보내면 현재 room과 실시간 점유가 해제되고, 방장이 복구하기 전에는 같은 세션에 재입장할 수 없다.
- 방장이 내보내기를 취소하고 새로 초대하면 해당 사용자가 다시 참가할 수 있다.
- 내보내기가 다른 세션과 사용자 관계에는 영향을 주지 않는다.
- 구조화 콘텐츠 정책, 소재 확인, 개인별 선호 저장, 사용자 관계 차단, 참가자 음소거가 제품 요구사항에 없다.

## UX-06. 플레이 일정과 단일 실시간 참여 제어

### 사용자 결과

- 사용자는 요일과 시간이 다른 여러 세션에 소속되거나 참가 신청할 수 있다.
- 세션 종료 시각을 미리 정하지 않고 시작 날짜와 시간만으로 다음 플레이 일정을 잡는다.
- 새 플레이의 시작 시각이 기존 신청·참석 일정과 6시간 이하로 가까우면 겹칠 가능성을 확인한 뒤 계속 진행한다.
- 여러 세션의 대기실이 동시에 열려 있어도 사용자는 실제 대기실·플레이 공간 하나만 점유한다.
- 플레이 사이에는 세션 소속과 진행 상태를 유지한 채 일정 조율, 지난 내용 확인, GM 준비를 수행한다.

### 확정 제품 규칙

`세션 참가`를 하나의 Boolean으로 취급하지 않고 다음 세 단계로 분리한다.

| 개념 | 허용 범위 | 의미 |
| --- | --- | --- |
| 세션 소속 | 여러 개 | 세션 구성원, 캐릭터와 진행 기록 보유 |
| 플레이 일정 신청·참석 | 여러 개, 근접 시 경고 | 특정 시작 시각의 플레이에 참여 의사 표시 |
| 실시간 참여 | 사용자당 하나 | 대기실 또는 플레이 room을 실제 점유 |

- 세션 홈이나 공개 상세를 열람하는 것은 실시간 참여로 계산하지 않는다.
- 세션이 `LOBBY_OPEN`으로 바뀌어도 모든 구성원을 자동으로 실시간 참여자로 만들지 않는다.
- 사용자가 대기실 입장을 확정하거나 진행 중인 플레이에 재입장할 때 실시간 점유를 획득한다.
- 종료 시각은 일정 입력, 참가 신청, 방장 일정 확정의 필수값이 아니다.
- 6시간 기준은 실제 충돌을 단정하는 값이 아니라 사용자 주의를 위한 제품 정책값이다.

### 세션 상태와 화면 접근

내부 상태와 사용자 표시명을 다음처럼 사용한다.

| 내부 상태 | 사용자 표시명 | 세션 홈 | 실시간 대기실 | 준비 완료 | 플레이 행동 |
| --- | --- | --- | --- | --- | --- |
| `DORMANT` | 대기 중 | 구성원 접근 가능 | 접근 불가 | 불가 | 불가 |
| `LOBBY_OPEN` | 입장 가능 | 접근 가능 | 구성원이 직접 입장 | 가능 | 불가 |
| `PLAYING` | 진행 중 | 접근 가능 | 기존 구성원 재입장 | 변경 불가 | 가능 |
| `COMPLETED` | 세션 완료 | 읽기 전용 | 불가 | 불가 | 불가 |
| `DISBANDED` | 세션 종료 | 읽기 전용 또는 정책에 따라 숨김 | 불가 | 불가 | 불가 |

`비활성`은 시스템 설명에만 사용하고 사용자 상태명은 `대기 중`으로 통일한다. `준비 중`은 GM 콘텐츠 준비와 혼동될 수 있으므로 대기실에 들어갈 수 있는 상태는 `입장 가능`으로 표시한다.

### 세션 홈과 실시간 대기실 분리

1. 세션 홈
   - 플레이 상태와 관계없이 구성원이 접근한다.
   - 다음 플레이 일정, 일정 제안, 참석·불참·미정 응답, 지난 플레이 요약, 참가 캐릭터, 참가자, 공지, 세션 탈퇴를 제공한다.
   - GM 전용 시나리오·노드·맵 준비는 `DORMANT`에서도 가능하며 플레이어에게 비공개인 정보를 유지한다.
   - 공개 모집 중인 세션은 비구성원에게 모집 정보와 참가 신청만 보여 준다.
2. 실시간 대기실
   - `LOBBY_OPEN`에서만 새로 입장할 수 있다.
   - 현재 접속자, 이번 플레이 일정 참석 상태, 캐릭터 최종 확인, 준비 완료, 방장의 플레이 시작을 제공한다.
   - `DORMANT`에서 실시간 URL로 직접 접근하면 세션 홈으로 보내고 다음 플레이 일정 또는 일정 미정 상태를 안내한다.
   - `PLAYING`에서는 기존 구성원의 재접속을 허용한다. 신규 사용자의 자동 가입은 막되 방장이 명시적으로 승인하면 현재 플레이 또는 다음 플레이부터 합류시킬 수 있다.
3. 참석 응답과 준비 완료
   - 참석·불참·미정은 예약 후 비동기로 제출하는 플레이 일정별 응답이다.
   - 준비 완료는 대기실에 실제 입장한 사용자가 현재 플레이에만 설정하는 실시간 상태다.
   - `DORMANT` 전환 또는 진행 저장 후 닫기 시 준비 상태를 초기화한다.

### 데이터 모델 계획

기존 `Session`은 소속 구성원과 지속되는 진행 상태를 보관하고 날짜별 플레이 약속과 실제 진행을 `SessionPlay`로 분리한다.

1. `Session`
   - 세션 기본 정보, 소속 구성원, 캐릭터, 시나리오 진행 상태를 유지한다.
   - 활동 상태 `DORMANT | LOBBY_OPEN | PLAYING | COMPLETED | DISBANDED`를 가진다.
   - 모집 상태와 활동 상태를 분리한다.
     - `recruitmentStatus: OPEN | CLOSED`
     - `joinPolicy: INVITE_ONLY | APPROVAL_REQUIRED | OPEN_JOIN`
   - `currentPlayId`와 목록용 `nextSessionAt` projection을 가진다.
2. 신규 후보 `SessionPlay`
   - `id`, `sessionId`, `sequence`.
   - `status: SCHEDULED | LOBBY_OPEN | PLAYING | FINISHED | CANCELLED`.
   - `scheduledStartAt`, `lobbyOpensAt`, `startedAt`, `endedAt`, `timeZone`.
   - `scheduleVersion`, `createdByUserId`, 생성·변경 시각.
   - 예정 종료 시각과 예상 플레이 시간은 필수 계약에 포함하지 않는다.
3. 신규 후보 `SessionPlayAttendance`
   - `playId`, `participantId` 복합 unique.
   - `attendance: ATTENDING | ABSENT | TENTATIVE`.
   - `isReady`, `readyAt`, `enteredLobbyAt`.
   - 기존 `SessionParticipant.isReady`, `readyAt`은 전환 기간 이후 제거하거나 현재 플레이 projection으로만 유지한다.
4. 신규 후보 `SessionApplication`
   - 공개 모집의 신청, 승인, 거절, 사용자 최종 취소를 세션 소속과 분리한다.
   - `PENDING | APPROVED | REJECTED | WITHDRAWN`과 신청·해결 시각을 저장한다.
   - 진행 중 승인에서는 `joinTiming: CURRENT_PLAY | NEXT_PLAY`를 함께 기록한다.
   - 초대형 세션은 초대 수락을 통해 바로 구성원이 될 수 있지만 같은 시간 근접 경고를 적용한다.
5. 신규 후보 `UserActivePlay`
   - `userId`를 unique로 두고 `playId`, `sessionId`, `acquiredAt`, `heartbeatAt`을 저장한다.
   - 모든 브라우저 탭과 기기를 합친 실시간 점유의 서버 권위 원천으로 사용한다.

`Session.nextSessionAt`은 다음 유효 플레이 일정을 빠르게 정렬·표시하기 위한 projection으로 유지하되 일정 이력의 원본으로 사용하지 않는다.

### 약속형과 공개 모집형

활동 상태, 공개 범위, 모집 상태, 참가 정책을 독립적으로 조합한다.

| 항목 | 이미 약속된 그룹 | 공개 모집 세션 |
| --- | --- | --- |
| `visibility` | `PRIVATE` | `PUBLIC` |
| `joinPolicy` | `INVITE_ONLY` | 기본 `APPROVAL_REQUIRED`, 선택적 `OPEN_JOIN` |
| 초기 `recruitmentStatus` | `CLOSED` | 정원까지 `OPEN` |
| `DORMANT` 비구성원 행동 | 유효한 초대 확인·수락 | 상세 조회·참가 신청 |
| `LOBBY_OPEN` 입장 | 초대 수락 구성원 | 승인·가입된 구성원 |
| `PLAYING` 신규 가입 | 방장 승인 시 허용 | 자동 가입은 차단하고 방장이 현재 또는 다음 플레이 합류를 선택 |

공개 모집의 기본 흐름은 `참가 신청 → 방장 승인 → 세션 구성원 확정`이다. 참가 신청 자체는 실시간 점유를 만들지 않으며, 일정이 없는 세션은 가입 이후 다음 플레이 일정이 정해질 때 참석 여부를 다시 받는다.

### 플레이 일정과 상태 전환

1. 일정 제안
   - 기존 campaign calendar의 `propose_schedule`, `respond_schedule`, `confirm_schedule` 개념을 재사용한다.
   - 사용자에게 필수로 받는 값은 시작 날짜·시각과 시간대다.
   - 종료 시각과 예상 소요 시간은 요구하지 않는다.
2. 일정 확정
   - 방장 확정 시 `SessionPlay(status=SCHEDULED)`를 생성하거나 schedule version을 올린다.
   - `Session.nextSessionAt`을 다음 유효 플레이 시작 시각으로 갱신한다.
   - 대기실 개방은 시작 시각과 같게 하거나 시스템 기본 선행 시간으로 자동 계산한다. 사용자가 개방 시각을 별도로 입력하도록 강제하지 않는다.
3. 대기실 개방
   - `lobbyOpensAt`에 idempotent scheduler가 `LOBBY_OPEN`으로 전환한다.
   - 자동 전환은 대기실만 열며 플레이를 자동 시작하지 않는다.
   - 방장은 `대기실 열기`로 예약 전 수동 개방할 수 있다.
4. 플레이 시작
   - 방장만 `PLAYING`으로 전환한다.
   - 현재 접속자, 캐릭터 선택 여부, 참석 응답과 준비 상태를 방장에게 보여 준다.
   - 미응답·미접속·미준비 참가자가 있으면 알리되 플레이 시작을 차단하지 않는다.
   - 최종 시작 여부는 방장이 결정하며 시스템이 최소 인원이나 필수 준비 조건을 강제하지 않는다.
5. 진행 저장 후 닫기
   - 사용자 행동명은 `진행 저장 후 닫기`로 한다.
   - 새 행동 입력 차단 → 처리 중 상태 변경 정리 → AI late response 폐기 → snapshot/checkpoint 저장 → 지난 플레이 요약 생성 → 준비 상태 초기화 → room 종료 순으로 처리한다.
   - 현재 `SessionPlay`를 `FINISHED`, 세션을 `DORMANT`로 전환한다.
   - 같은 날을 포함해 언제든 대기실을 다시 열거나 다음 플레이 일정을 잡을 수 있으며, 일정 미정 상태로 남길 수도 있다.
### 시작 시간 6시간 근접 경고

종료 시각이 없으므로 실제 일정 충돌을 판정하지 않는다. `SESSION_START_PROXIMITY_WARNING_HOURS = 6` 정책값을 기준으로 주의를 제공한다.

1. 경고 시점
   - 공개 세션 참가 신청.
   - 초대 세션의 초대 수락.
   - 확정된 플레이 일정에 `ATTENDING` 응답.
   - 일정 변경으로 새로운 6시간 근접 관계가 생긴 경우.
2. 비교 대상
   - 미래 시작 시각을 가진 사용자 제출 참가 신청.
   - 승인된 세션의 다음 유효 플레이 일정.
   - 초대를 수락한 세션의 다음 유효 플레이 일정.
   - `ATTENDING`으로 응답한 플레이 일정과 이미 열린 플레이.
   - 거절·취소·완료된 플레이, 단순 미수락 초대, `ABSENT` 응답은 제외한다.
3. 계산
   - 새 `scheduledStartAt`과 비교 대상 시작 시각의 절대 차이가 6시간 이하이면 경고한다.
   - UTC instant로 계산하므로 자정을 넘긴 두 플레이 일정도 정확히 비교한다.
   - 같은 시각의 여러 근접 일정이 있으면 모두 사용자 표시명과 지역 시각으로 보여 준다.
4. 사용자 선택
   - 경고는 참가·참석·예약을 차단하지 않는다.
   - `앞 세션이 끝나지 않았으면 직접 퇴장한 뒤 다음 세션에 입장해야 한다`는 점을 checkbox로 확인한다.
   - `돌아가기`와 `확인하고 신청/참석하기`를 구분한다.
5. 확인 기록
   - 확인 시각과 비교한 플레이 일정·schedule version을 기록한다.
   - 시작 시각이 변경되면 기존 참석 응답은 유지하고 참가자에게 변경 사실을 알린다.
   - 일정 변경으로 새 6시간 근접 관계가 생긴 사용자에게만 근접 경고를 다시 확인하게 한다.
   - 한 사용자의 근접 일정 때문에 방장의 일정 확정이나 다른 참가자의 대기실 개방을 막지 않는다.

권장 문구:

> 신청한 세션 중 `검은 우물의 쥐떼`가 같은 날 오후 2시에 시작됩니다. 새 세션은 오후 7시에 시작되어 두 시작 시각의 간격이 5시간입니다. 앞 세션이 길어지면 늦을 수 있으며 두 세션에 동시에 입장할 수 없습니다.

### API 계약 후보

1. 플레이 일정 조회·예약
   - `GET /sessions/:id/plays?status=future`: 예정·현재 플레이와 viewer attendance 조회.
   - `POST /sessions/:id/plays`: 방장이 시작 시각·시간대로 다음 플레이 일정 생성.
   - `PATCH /sessions/:id/plays/:playId`: 시작 시각 변경과 schedule version 증가.
   - `POST /sessions/:id/plays/:playId/cancel`: 플레이 일정 취소.
2. 플레이 상태 변경
   - `POST /sessions/:id/plays/:playId/open-lobby`: 대기실 열기.
   - `POST /sessions/:id/plays/:playId/start`: 플레이 시작.
   - `POST /sessions/:id/plays/:playId/finish`: 진행 저장 후 닫기.
   - 모든 상태 변경 요청은 `expectedScheduleVersion` 또는 `expectedStateVersion`을 받아 오래된 조작을 거절한다.
3. 참석 응답
   - `PATCH /sessions/:id/plays/:playId/attendance/me`에 `ATTENDING | ABSENT | TENTATIVE`를 전송한다.
   - `ATTENDING` 요청에 근접한 플레이 일정이 있으면 상태를 바꾸지 않고 `SESSION_SCHEDULE_PROXIMITY_CONFIRMATION_REQUIRED`와 표시용 일정 목록, 일회성 confirmation token을 반환한다.
   - 사용자가 확인한 재요청은 token이 참조한 모든 schedule version이 그대로일 때만 적용한다. 변경됐다면 최신 목록으로 다시 확인한다.
4. 공개 참가 신청·초대 수락
   - `POST /sessions/:id/applications`와 초대 수락 요청에도 같은 confirmation token 흐름을 사용한다.
   - 방장의 승인 요청은 `joinTiming: CURRENT_PLAY | NEXT_PLAY`를 받아 즉시 합류와 다음 플레이 합류를 구분한다.
   - 근접 경고는 성공 응답 뒤 toast로 알리는 방식이 아니라 mutation 전에 사용자가 선택할 수 있는 사전 확인으로 처리한다.
5. 실시간 입장·전환
   - `POST /sessions/:id/plays/:playId/enter`가 사용자 실시간 점유를 획득한다.
   - 다른 점유가 있으면 상태를 바꾸지 않고 `SESSION_ACTIVE_PLAY_CONFLICT`와 현재 플레이 표시 정보를 반환한다.
   - `POST /sessions/:id/plays/:playId/switch-entry`는 일회성 switch token을 검증한 뒤 이전 room 해제와 새 점유를 한 transaction으로 처리한다.
   - heartbeat와 비정상 종료 감지는 Socket 연결 계층에서 갱신하고 REST 응답과 같은 서버 권위 점유를 사용한다.

### 단일 실시간 참여

1. 점유 획득
   - 대기실 입장 확인 또는 진행 중 플레이 재입장 시 서버가 `UserActivePlay`를 transaction으로 획득한다.
   - 같은 플레이의 다른 탭·기기 재접속은 동일 점유로 취급하되 사용자 화면 중복 제어 정책을 적용한다.
2. 다른 플레이를 이미 점유 중인 경우
   - 자동으로 이전 플레이를 떠나지 않는다.
   - 현재 플레이 이름과 새 플레이 이름을 보여 주고 `현재 플레이로 돌아가기` 또는 `현재 플레이에서 나가고 새 플레이 입장`을 선택하게 한다.
   - 전환 확인 시 이전 room leave와 점유 해제 후 새 점유 획득을 원자적으로 처리한다.
3. 점유 해제
   - 사용자의 명시적 플레이 화면 나가기, 진행 저장 후 닫기, 세션 내보내기 시 즉시 해제한다.
   - 비정상 연결 종료는 heartbeat 만료 후 해제하며 단순 네트워크 흔들림으로 즉시 다른 플레이 점유를 허용하지 않는다.
   - 세션 탈퇴와 플레이 화면 나가기는 별도 행동으로 유지한다.
4. 시간이 실제로 겹친 경우
   - 앞 플레이가 길어져도 다음 세션의 대기실 개방이나 다른 참가자의 플레이를 막지 않는다.
   - 해당 사용자에게 다음 플레이 시작 안내를 보여 주되 자동 강제 이동하지 않는다.
   - 사용자는 앞 플레이를 나온 뒤에만 다음 실시간 대기실에 입장한다.
5. 이벤트 격리
   - FE는 route와 현재 play ID가 일치하는 이벤트만 현재 snapshot에 적용한다.
   - 전환 후 이전 room의 늦은 이벤트는 로그·전투·캐릭터 상태를 변경하지 않는다.

### 기존 데이터 전환

1. migration 전 dry-run
   - 기존 `SessionStatus`별 건수와 `nextSessionAt` 유무를 집계한다.
   - 기존 `PAUSED` 세션은 실제 플레이가 이어지고 있는지 플레이 사이 대기인지 코드만으로 구분할 수 없으므로 ID와 사용자 표시명을 별도 검토 목록으로 출력한다.
   - 기존 참가자별 `isReady`, `readyAt`은 현재 플레이의 준비 상태로 신뢰하지 않고 초기화 대상 수만 보고한다.
2. 상태 매핑
   - `RECRUITING`은 `activityStatus=DORMANT`, `recruitmentStatus=OPEN`으로 전환한다.
   - `PLAYING`은 `activityStatus=PLAYING`과 legacy current play를 생성한다. 실제 시작 시각을 추측하지 않고 `startedAt=null`, migration marker를 허용한다.
   - `PAUSED`는 자동 일괄 분류하지 않는다. 검토 결과에 따라 계속 진행할 `PLAYING` 또는 플레이 사이의 `DORMANT`로 명시 전환한다.
   - `COMPLETED`, `DISBANDED`는 terminal 상태를 유지하고 실시간 점유를 만들지 않는다.
3. 일정 매핑
   - 미래 `nextSessionAt`이 있는 비종료 세션에는 해당 시각의 `SCHEDULED` `SessionPlay`를 한 건 생성한다.
   - `nextSessionAt`이 없으면 임의 일정을 만들지 않고 `일정 미정`으로 둔다.
   - 종료 시각과 예상 소요 시간을 legacy 값에서 추론하거나 backfill하지 않는다.
4. 참가자·점유
   - 기존 `SessionParticipant`는 세션 소속으로 그대로 보존한다.
   - 기존 ready 값은 새 `SessionPlayAttendance`로 복사하지 않고 `false/null`로 시작한다.
   - `UserActivePlay`는 backfill하지 않고 사용자의 다음 실시간 입장 시 획득한다.
   - 기존 세션 소속을 공개 참가 신청으로 역변환하지 않는다.
5. 전환 gate
   - 두 번째 backfill apply에서 신규 `SessionPlay`와 상태 갱신 대상이 0건이어야 한다.
   - `Session.nextSessionAt` projection과 미래 `SessionPlay`의 최소 시작 시각이 일치해야 한다.
   - active play가 없는 세션이 `LOBBY_OPEN/PLAYING` projection으로 남지 않아야 한다.
   - 사용자별 `UserActivePlay` unique 위반이 없어야 한다.

### 실패 처리와 경계 조건

- 일정 변경과 대기실 자동 개방이 동시에 실행되면 schedule version이 맞는 작업 하나만 성공한다.
- scheduler 지연으로 개방 시각을 지난 작업은 현재 플레이 상태와 취소 여부를 다시 확인한 뒤 idempotent하게 처리한다.
- 방장이 수동으로 대기실을 연 뒤 예약 작업이 도착해도 중복 플레이나 중복 이벤트를 만들지 않는다.
- 일정이 없는 세션은 근접 비교에서 제외하고 다음 플레이 일정이 확정될 때 참석 응답을 받는다.
- 시작 시각이 정확히 6시간 차이거나 자정을 넘겨 6시간 이하인 경우에도 경고한다.
- 일정 변경으로 새 근접 관계가 생겨도 참가 신청이나 세션 소속을 자동 취소하지 않는다.
- 다른 기기에서 이미 플레이를 점유 중이면 새 기기 입장은 서버 응답 기준으로 차단·전환한다.
- stale heartbeat를 해제하기 전에 현재 Socket 연결과 플레이 상태를 재확인한다.
- `진행 저장 후 닫기` 중 처리 중인 AI 응답은 새 상태 version에 적용되지 않으며 같은 플레이를 두 번 닫아도 결과가 같다.
- 방장 부재나 일부 참가자 미접속 때문에 대기실 자체를 자동 종료하지 않는다. 취소·재예약은 방장 또는 명시된 운영 정책으로 수행한다.

### 완료 조건

- 한 사용자가 월요일부터 일요일까지 서로 다른 7개 세션의 구성원이 될 수 있다.
- 종료 시각을 입력하지 않고 각 세션의 다음 플레이 시작 시각을 예약할 수 있다.
- 기존 미래 플레이 일정과 시작 간격이 6시간 이하이면 근접 경고가 나오고 확인 후 신청을 계속할 수 있다.
- 시작 간격이 6시간을 초과하면 근접 경고가 나오지 않는다.
- 자정을 넘긴 5시간 차이의 플레이 일정에도 근접 경고가 나온다.
- 일정이 바뀌어도 기존 참석 응답은 유지되며, 새 6시간 근접 관계가 생긴 사용자만 경고를 다시 확인한다.
- 두 세션의 대기실이 동시에 열려도 다른 사용자들은 각각 정상 입장할 수 있다.
- 같은 사용자는 다른 탭·브라우저·기기를 포함해 실시간 플레이 하나만 점유한다.
- 사용자가 현재 플레이를 명시적으로 나온 뒤에는 다른 열린 플레이로 전환할 수 있다.
- 앞 플레이가 늦게 끝나도 다음 플레이의 개방과 다른 참가자의 진행은 차단되지 않는다.
- `DORMANT`에서는 세션 홈과 GM 준비는 가능하지만 준비 완료와 플레이 행동은 불가능하다.
- `LOBBY_OPEN`에서 설정한 준비 완료는 진행 저장 후 닫을 때 초기화된다.
- `진행 저장 후 닫기` 후 진행 상태가 checkpoint로 보존되고 세션이 `DORMANT`로 돌아간다.
- 이전 플레이의 늦은 Socket 이벤트가 현재 플레이 snapshot과 로그에 섞이지 않는다.
- 완료 세션은 이어하기에 나오지 않지만 권한 있는 사용자가 기록으로 열 수 있다.

### 사용자 결과

- 비개발자 GM이 raw ID, flag key, enum을 몰라도 짧은 시나리오를 만들고 검증·공개한다.
- 상세 조건과 공개 설정이 필요해도 내부 구현 값을 직접 입력하지 않고 사용자용 선택지로 설정한다.
- 사람 GM은 플레이 중 자주 쓰는 진행 작업을 적은 클릭으로 실행한다.

### 구현 작업

1. 내부 구현 값 제거
   - 편집기는 별도의 기본·고급 모드로 나누지 않고 하나의 작성 흐름을 사용한다.
   - 작성 흐름은 기본 정보 → 공개 메타데이터 → 장면 → NPC/단서 → 판정/전환 → 미리보기 → 공개 순서로 구성한다.
   - node ID, flag key, raw enum은 저장·실행 계층에서만 사용하고 편집 화면에서는 장면 제목, 조건 설명, 사용자용 선택지로 변환한다.
2. `fe/src/pages/ScenarioEditorPage.tsx`
   - 4천 줄 규모 페이지를 단계별 section/component와 form state hook으로 분리한다.
   - `window.prompt`, `window.confirm`을 검증 가능한 dialog form으로 교체한다.
   - 공개 범위, 변경 요약, 권리 확인, fork 허용을 한 공개 dialog에서 받는다.
3. 사용자용 선택지
   - `AUTO_REVEAL`, flag key, node ID를 직접 입력시키는 대신 사용자 설명이 있는 select/template을 제공한다.
   - raw 입력란은 일반 제품 UI에 제공하지 않고 필요한 표현력은 조건 선택기와 템플릿으로 지원한다.
4. 검증
   - 공개 전 오류는 node ID가 아니라 장면 제목과 수정 링크로 표시한다.
   - 예상 시간과 권장 인원은 작성자가 제공한 경우에만 검증하고 필수 입력으로 강제하지 않는다.
5. 사람 GM 패널
   - 메시지, NPC 발화, 현재 장면 선택·다음 장면 이동, 자료 공개, 전투 시작을 1차 행동으로 묶는다.
   - 구조화 시나리오를 사용할 때만 장면 선택을 표시하며 일반 대화와 서술마다 장면 변경을 요구하지 않는다.
   - 세션 완결·보관 화면의 `P6`, archive ID, current node ID를 사용자 용어로 바꾼다.

### 완료 조건

- 편집기에서 내부 ID나 flag key를 직접 입력하지 않고 최소 3장면 시나리오를 공개할 수 있다.
- 공개 dialog를 취소해도 draft가 손상되지 않는다.
- validation 오류에서 해당 장면 편집 위치로 바로 이동한다.
- 사람 GM이 현재 장면을 확인한 상태에서 주요 운영 행동을 두 번 이내의 조작으로 실행한다.

## UX-10. 데스크톱 웹 접근성

### 지원 범위

- 이 프로젝트는 데스크톱 웹 브라우저만 지원한다.
- 모바일 전용 레이아웃, 모바일 플레이 탭, 터치 중심 VTT 조작, 작은 화면 대응은 구현하지 않는다.
- 접근성 개선은 데스크톱 환경의 키보드, 초점, 의미 구조, 색상, 화면 확대, 스크린 리더 사용을 대상으로 한다.

### 공개 베타 차단 범위

- 로그인, 홈, 세션 탐색, 생성, 초대 참가, 캐릭터 선택, 기본 행동 입력을 키보드만으로 완료한다.
- dialog는 초점 진입, Tab 순환, Escape 닫기, 닫은 뒤 초점 복귀를 지원한다.
- `article role="button"` 같은 가짜 버튼은 실제 `button` 또는 `a`로 교체한다.
- 오류·선택·상태를 색상만으로 전달하지 않는다.
- 지원하는 데스크톱 화면에서 200% 확대해도 핵심 문구와 조작 요소를 사용할 수 있다.

### P1 확장 범위

1. VTT 대체 조작
   - drag 전용 토큰 이동에 토큰 선택 + 방향/거리 입력 또는 키보드 이동 패널을 추가한다.
   - 맵을 사용하지 못해도 텍스트 행동 입력으로 같은 핵심 게임 행동을 수행할 수 있게 한다.
2. 시각·운동
   - WCAG 2.2 AA 대비, `prefers-reduced-motion`, 스크린 리더용 live region을 적용한다.
3. 자동 검증 기반
   - FE에 Vitest, React Testing Library, axe 기반 검사와 최소 Playwright 접근성 smoke 흐름을 추가한다.
   - `fe/package.json`에 test script를 명시한다.

### 완료 조건

- 키보드만으로 공개 세션을 찾아 참가하고 첫 행동을 전송할 수 있다.
- VTT 토큰을 drag하지 않고도 이동 요청을 만들 수 있다.
- 데스크톱 화면에서 200% 확대해도 로그인부터 첫 행동까지 필요한 정보를 읽고 조작할 수 있다.
- 핵심 화면 axe 자동 검사에서 serious/critical 위반이 0건이다.

## UX-11. 계정과 사전 조율

### P0 범위

1. OAuth 계정 탈퇴
   - 로컬 계정은 현재 비밀번호를 확인한다.

   - `canDeleteAccount`는 provider별 실제 가능한 흐름과 일치해야 한다.

   - 게스트 로그인 버튼 근처, 최초 방문 튜토리얼 전, 계정 화면에 7일 보존 정책을 일관되게 표시한다.

### P1 범위

1. 비밀번호 관리
   - `PATCH /users/me/password`로 로그인 상태 변경을 지원한다.
   - reset token은 hash 저장, 짧은 만료, 1회 사용으로 구현한다.

   - 이메일 발송 provider interface와 실패 재시도 정책을 정의한다.

3. 참가 메모
   - 세션 참가 전 호스트에게 전달할 짧은 신청 메모를 지원하되 자유 형식 DM으로 확장하지 않는다.

- LOCAL, KAKAO, DISCORD, GUEST 계정이 각각 맞는 확인 방식으로 탈퇴를 완료할 수 있다.
- 비밀번호 재설정 token 재사용과 만료 후 사용이 거절된다.

## 8. 데이터 전환 계획

### migration이 필요한 작업

- 시나리오 공개 메타데이터 정규화
- 온보딩 진행 상태
- 세션 활동·모집 상태와 플레이 일정·참석 상태
- 공개 참가 신청과 시작 시간 근접 경고 확인 이력
- 사용자별 단일 실시간 플레이 점유
- 비밀번호 reset token 또는 인증 challenge

### 전환 원칙

- 모든 backfill은 기본 dry-run이며 명시적인 apply에서만 쓴다.
- 시나리오 메타데이터는 구조화 컬럼 coverage가 100%가 되기 전 read source를 전환하지 않는다.
- 계정 provider에 따른 탈퇴 가능 여부를 backfill로 임의 변경하지 않는다.
- migration과 backfill 적용은 이 계획의 문서 작성 범위에 포함하지 않는다.

## 9. 공통 완료 정의

각 작업은 다음을 모두 만족해야 완료다.

- shared DTO, decoder, FE type, BE validation이 같은 계약을 사용한다.
- 권한 없는 요청, 중복 요청, 오래된 응답, 빈 결과, 네트워크 실패를 처리한다.
- loading, empty, error, disabled 상태가 사용자 문구로 구분된다.
- 사용자 화면에 내부 ID와 raw enum이 노출되지 않는다.
- 데스크톱 키보드 접근과 focus 관리를 확인한다.
- 민감한 원문을 로그·분석 이벤트에 추가하지 않는다.
- 필요한 migration은 dry-run과 재실행 멱등성을 확인한다.
- 자동 검증 코드와 수동 검증 시나리오를 함께 추가한다.
- `structure/SCREEN.md`, `structure/QUALITY_MVP_ACCEPTANCE.md` 등 기준 문서를 실제 구현과 맞춘다.
- 사용자가 테스트를 실행하고 결과를 기록하기 전에는 `동적 검증 완료`로 표시하지 않는다.

## 10. 사용자 검증 계획

프로젝트 규칙에 따라 이 문서 작성 과정에서는 테스트를 실행하지 않았다. 구현 후 사용자가 변경 범위에 맞춰 다음 검증을 직접 실행한다.

```powershell
npm run build -w @trpg/shared-types
npm run build -w @trpg/be
npm run build -w @trpg/fe
npm run test:e2e
npm run test:p6-regression
```

```powershell
npm run test -w @trpg/fe
```

### 필수 수동 여정

1. 공개 세션을 12개 이상 준비하고 11번째 세션을 검색·필터·페이지 이동으로 연다.
2. 공개/비공개 세션을 만들고 설명·일정·총 인원을 수정한 뒤 새 브라우저에서 초대 링크로 참가한다.
3. 신규 게스트가 최초 방문 튜토리얼을 시작해 기존 캐릭터 생성 → 세션 생성 → AI GM·1인 구성 → 첫 행동 → `/힌트` → `/요약`을 완료한다. 다른 신규 계정은 튜토리얼을 건너뛰고 기존 메뉴를 제한 없이 사용하는지 확인한다.
4. 로그아웃·로그인 또는 다른 브라우저에서 같은 세션을 홈 `이어하기`로 재개한다.
5. 한 계정을 서로 다른 요일의 7개 세션에 가입시키고, 종료 시각 없이 다음 플레이 일정을 각각 잡는다. 시작 시각이 6시간 이하로 가까운 신청에는 경고가 나오되 계속 신청할 수 있는지 확인한다. 두 대기실을 동시에 연 뒤 같은 계정은 하나만 입장하고, 명시적으로 나온 후 다른 플레이로 전환하며 이전 이벤트가 섞이지 않는지 확인한다. 일정 변경 후 기존 참석 응답은 유지되고 새 근접 관계가 생긴 경우에만 경고가 다시 나오는지 확인한다.
6. 세션 설명이 생성·탐색·상세·초대 미리보기에 동일하게 보이는지 확인한다. 플레이 화면 나가기는 세션 소속을 유지하고, 세션 탈퇴는 `LEFT`, 방장 내보내기는 `KICKED`가 되는지 확인한다. 내보낸 사용자의 자동 재입장은 막히지만 방장이 복구하고 새로 초대하면 다시 참가할 수 있는지 역할별 계정으로 확인한다.
7. LOCAL/KAKAO/DISCORD/GUEST 계정 탈퇴와 비밀번호 복구를 provider별로 확인한다.
8. 마우스 없이 로그인 → 세션 검색 → 참가 → 캐릭터 선택 → 첫 행동을 완료한다.
9. 지원하는 데스크톱 화면의 200% 확대에서 행동 입력, 세션 설명, 플레이 화면 나가기, 세션 탈퇴, 방장 내보내기를 사용할 수 있는지 확인한다.

## 11. 공개 베타 판정

다음 조건 중 하나라도 충족하지 못하면 공개 베타 대신 초대형 비공개 알파를 유지한다.

- [ ] 공개/내 세션 목록이 10건을 넘어도 누락되지 않는다.
- [ ] 세션 생성·수정·비공개 초대 링크가 처음부터 끝까지 동작한다.
- [ ] 신규 사용자가 최초 방문 튜토리얼을 완료하거나 건너뛸 수 있고, 재방문해 기존 세션을 이어서 플레이한다.
- [ ] 시나리오 상세가 실제 메타데이터만 표시하고 내부 테스트 콘텐츠를 숨긴다.
- [ ] 세션 설명, 참가자의 세션 탈퇴, 방장의 세션 내보내기·자동 재입장 방지·명시적 복구가 동작한다.
- [ ] 일반 사용자 화면의 내부 ID/raw enum과 준비 중 주요 메뉴가 제거된다.
- [ ] OAuth 포함 모든 계정 유형이 탈퇴할 수 있고 게스트 보존 정책이 사전 고지된다.
- [ ] 키보드로 로그인부터 첫 행동까지 완료할 수 있다.
- [ ] 핵심 자동 회귀, E2E, 수동 사용자 여정의 검증 증거가 기록되어 있다.

## 12. 구현 전 확정이 필요한 외부 결정

다음 항목은 코드만으로 정답을 만들 수 없어 담당자의 제품·운영 결정이 필요하다.

1. 이메일 발송 제공자
   - 비밀번호 재설정과 이메일 확인을 실제로 전달할 provider, 발송 실패·재시도·rate limit 정책을 정해야 한다.

이 결정이 나기 전에도 인터페이스와 로컬 stub은 만들 수 있지만, 사용자에게 이메일 복구를 완료 기능처럼 안내해서는 안 된다.
