## 1. 결론

현재 프로젝트는 캐릭터 생성·성장, AI/사람 GM, 판정·전투·VTT, 실시간 로그, 시나리오 제작처럼 실제 TRPG를 진행하기 위한 코어 기능이 넓게 구현되어 있다. 그러나 사용자가 처음 방문해 세션을 찾고, 안전하게 참가하고, 다음 방문에서 이어서 플레이하는 제품 흐름은 공개 베타 기준에 미치지 못한다.

따라서 다음 개발 사이클에서는 룰과 콘텐츠의 폭을 더 넓히기보다 아래 다섯 결과를 먼저 달성한다.

1. 처음 온 사용자가 5분 이내에 AI GM과 첫 의미 있는 행동을 수행한다.
2. 공개 세션이 10개를 넘어도 검색·필터·페이지 이동 결과가 누락되지 않는다.
3. 방장이 공개/비공개 세션을 만들고 수정한 뒤 실제 링크로 초대할 수 있다.
4. 모르는 사람과 플레이하더라도 콘텐츠 경고, 안전 신호, 신고·차단·음소거·퇴장 수단이 있다.
5. 여러 캠페인에 참여한 사용자가 홈에서 원하는 세션을 골라 중단 지점부터 재개한다.

공개 베타는 P0 항목과 UX-10의 핵심 접근성 범위가 모두 완료된 뒤에만 시작한다. P0이 끝나기 전 외부 사용자를 받는 경우에는 초대 기반 비공개 알파로 한정한다.

## 2. 계획의 전제와 범위

### 전제

- 웹 플랫폼과 현재 AI/사람 GM 이중 구조를 유지한다.
- 게임 상태의 최종 권위는 기존처럼 규칙 엔진과 상태 엔진에 둔다.
- 일정은 팀 인원과 가용 시간이 정해지지 않았으므로 달력 대신 `S/M/L/XL` 상대 크기로 표기한다.
- 공개 세션에서 서로 모르는 사용자가 만나는 상황을 제품 범위로 본다.
- 이 문서는 2026-07-11 코드 정적 점검 결과를 기준으로 작성했다. 문서 작성 과정에서 테스트나 브라우저 수동 검증은 실행하지 않았다.

### 포함 범위

- 첫 사용자 온보딩과 AI GM 빠른 시작
- 홈의 이어하기와 다중 캠페인 전환
- 세션 검색, 필터, 페이지네이션, 정확한 전체 개수
- 세션 생성·수정·일정·공개 범위·초대 링크
- 시나리오 메타데이터와 제공 콘텐츠 큐레이션
- 공개 플레이 안전, 신고, 차단, 음소거, 퇴장
- AI 처리 상태, 취소, 재시도, 데이터 이용 고지
- 사람 GM과 시나리오 제작자의 기본 편집 흐름
- 사용자용 문구, 내부 ID 제거, 접근성, 모바일 웹
- 계정 복구, OAuth 계정 탈퇴, 게스트 보존 안내
- 사용자 여정 기반 계측과 공개 베타 검증

### 제외 범위

- 신규 룰셋, 클래스, 주문, 몬스터의 대규모 추가
- 네이티브 모바일 앱
- 유료 콘텐츠 마켓과 결제
- 사용자 간 자유 형식 DM
- 평점 기반 GM/플레이어 서열화
- 운영 배포, 운영 DB 변경, 외부 분석 서비스 계약

## 5. 공통 제품 결정

다음 결정은 개별 구현에서 다시 다르게 해석하지 않는다.

- 목록 검색·필터·정렬·페이지 계산은 서버가 수행한다. 프론트는 서버가 반환한 한 페이지를 다시 전체 목록처럼 필터하지 않는다.
- 초대 링크를 여는 동작만으로 세션 참가 상태를 변경하지 않는다. 제한된 미리보기를 보여 준 뒤 사용자가 참가를 확정한다.
- `maxParticipants`는 호환성을 위해 현재와 같이 호스트/사람 GM을 포함한 총 참여 인원으로 유지한다. 화면에는 반드시 `총 인원(GM/호스트 포함)`이라고 표시한다.
- 사용자가 여러 세션의 구성원일 수 있지만, 한 브라우저 탭에서 실시간으로 활성화하는 세션은 하나로 둔다. 전환할 때 이전 Socket room을 떠난 뒤 새 room에 참가한다.
- 시나리오 메타데이터가 없으면 `미정` 또는 항목 미표시를 사용한다. 제목이나 난이도로 플레이 시간·테마·입문자 적합성을 추측하지 않는다.
- 공개 베타에서 콘텐츠 경고와 안전 신호는 선택 장식이 아니라 기본 세션 기능으로 취급한다.
- AI 요청 취소 후 늦게 도착한 응답은 화면 표시뿐 아니라 상태 변경에도 사용하지 않는다.
- 사용자 화면에는 내부 ID, 저장용 key, raw enum을 표시하지 않는다. URL에 public ID가 필요하더라도 본문에는 렌더링하지 않는다.
- 자유 형식 DM은 이번 계획에 포함하지 않는다. 모집 전 조율은 공개 프로필의 선택형 정보와 세션 참가 메모로 제한한다.
- 계측 이벤트에는 행동 원문, 채팅 원문, AI 프롬프트, 안전 요청의 자유 입력 내용을 넣지 않는다.

## 6. 세부 구현 계획

## UX-01. 서버 기준 세션 탐색

### 사용자 결과

- 11번째 이후 세션도 검색과 페이지 이동으로 찾을 수 있다.
- 공개 세션 수와 내 세션 수가 실제 전체 개수와 같다.
- 검색어, GM 유형, 상태, 시나리오, 일정, 정렬을 바꾸면 서버 기준 결과가 일관되게 갱신된다.

### 구현 작업

1. `shared-types/src/dto/api/sessions.dto.ts`
   - `SessionListQueryDto`에 `query`, `gmMode`, `sort`를 추가한다.
   - `sort`는 우선 `recent`, `soonest`, `title`만 허용한다.
   - `page`, `size`, 필터의 최대 길이와 허용 값을 DTO에서 검증한다.
2. `be/src/modules/sessions/sessions.controller.ts`, `be/src/modules/sessions/sessions.service.ts`
   - 제목·설명·시나리오 제목 검색과 GM/상태 필터를 DB `where`에 반영한다.
   - 정렬에는 항상 안정적인 ID tie-breaker를 둔다.
   - `PUBLIC` 목록과 `내 세션`의 권한 조건을 별도 query builder로 유지한다.
3. `fe/src/services/sessionApi.ts`
   - `listSessions(params)`와 `listMySessions(params)`가 query를 직렬화한다.
   - 응답의 `content`, `page`, `totalElements`, `totalPages`를 모두 보존한다.
4. `fe/src/hooks/useSession.ts`
   - 목록 상태를 플레이 실시간 상태와 분리한 `useSessionCatalog` 후보 hook으로 이동한다.
   - 공개/내 세션의 페이지와 필터 상태를 별도로 관리한다.
   - 이전 요청보다 늦게 끝난 응답이 최신 화면을 덮지 않도록 요청 sequence 또는 `AbortController`를 사용한다.
5. `fe/src/pages/SessionDiscoverPage.tsx`, `fe/src/pages/LobbyPage.tsx`
   - 로컬 전체 목록 필터와 `slice()` 기반 페이지네이션을 제거한다.
   - 검색 입력은 250~400ms debounce 후 요청한다.
   - 페이지 번호, 전체 결과 수, 로딩, 결과 없음, 재시도 상태를 구분한다.

### 실패 처리

- 마지막 페이지에서 세션이 삭제되어 빈 페이지가 되면 유효한 마지막 페이지로 한 번만 재요청한다.
- 필터 요청 실패 시 기존 결과를 즉시 지우지 않고 오류와 재시도 버튼을 함께 보여 준다.
- 잘못된 page/size/sort는 400으로 거절하며 임의 보정하지 않는다.

### 완료 조건

- 공개 세션 12개를 만들었을 때 11번째와 12번째가 검색 및 페이지 이동으로 노출된다.
- 필터 적용 후 `totalElements`와 실제 반환 가능한 ID 집합이 일치한다.
- 홈 카운트가 현재 페이지 길이가 아니라 서버 전체 개수를 표시한다.
- 빠르게 검색어를 바꿔도 오래된 응답이 최신 결과를 덮지 않는다.

## UX-02. 세션 생성·수정·초대 완성

### 사용자 결과

- 방장은 제목, 설명, 시나리오, GM 유형, 총 인원 1~8명, 공개 범위, 다음 일정을 설정한다.
- 생성 후에도 모집 중인 세션의 정보를 수정한다.
- 초대받은 사용자는 `/join/:inviteCode` 링크에서 세션을 확인하고 참가한다.

### 구현 작업

1. `fe/src/services/sessionApi.ts`
   - positional argument 대신 `CreateSessionInput` 객체를 받도록 내부 API를 정리한다.
   - `description`, `visibility`, `nextSessionAt`, `maxParticipants`, `gmMode`를 빠짐없이 전송한다.
   - `PATCH /sessions/:id`를 호출하는 `updateSession()`을 추가한다.
2. `fe/src/pages/SessionCreatePage.tsx`
   - 설명, 공개/비공개, 다음 일정 필드를 추가한다.
   - 인원 범위를 서버와 같은 1~8로 맞추고 총 인원 의미를 명시한다.
   - AI GM과 사람 GM을 checkbox가 아닌 설명이 있는 단일 선택으로 바꾼다.
   - 시나리오 카드에 실제 예상 시간, 권장 레벨, 콘텐츠 경고를 표시한다.
3. `fe/src/pages/PlayPage.tsx`의 세션 설정 영역
   - 호스트만 볼 수 있는 편집 폼을 추가하고 서버 응답 성공 후 스냅샷을 병합한다.
   - 복사 값은 초대 코드가 아니라 `shareUrl` 전체를 우선한다.
   - 브라우저 origin으로 URL을 조립하는 fallback은 서버 `shareUrl`이 없을 때만 사용한다.
4. `fe/src/app/App.tsx`
   - `/join/:inviteCode`를 명시적으로 파싱한다.
   - 비로그인 사용자는 `returnTo`와 invite code를 보존한 뒤 로그인 화면으로 이동한다.
   - 로그인 후 제한된 미리보기 → 참가 확인 → 캐릭터 선택 → 입장 순서를 유지한다.
5. `be/src/modules/sessions`
   - 신규 후보 `GET /sessions/invites/:inviteCode/preview`에서 제목, GM 유형, 현재/최대 인원, 시나리오 요약, 콘텐츠 경고만 반환한다.
   - 실제 참가 변경은 기존 `POST /sessions/join-by-invite`에서만 수행한다.
   - 비공개 세션은 공개 목록에서 제외하지만 유효한 invite code 미리보기는 허용한다.
   - P1에서 초대 링크 회전을 지원하는 `POST /sessions/:id/invite/rotate`를 추가한다.

### 권한과 실패 처리

- 설정 변경은 호스트만 가능하며 참가 인원보다 작은 정원으로 낮출 수 없다.
- 사람 GM을 AI GM으로 바꾸거나 반대로 바꾸는 작업은 이미 플레이가 시작된 뒤에는 차단한다.
- 만료·회전·오타 코드에는 세션 존재 여부를 과도하게 노출하지 않는 동일한 사용자 메시지를 사용한다.
- 링크 미리보기는 참가자 목록, 로그, 비공개 노트, 내부 ID를 반환하지 않는다.

### 완료 조건

- 공개/비공개 세션을 각각 만들고 새로고침 후 모든 입력값이 유지된다.
- 생성한 세션을 수정하면 목록·상세·플레이 설정에 같은 값이 보인다.
- 로그아웃 상태에서 초대 링크를 연 뒤 로그인해도 같은 초대 흐름으로 복귀한다.
- 링크를 열기만 해서는 참가자가 추가되지 않는다.
- 링크 복사 결과를 새 브라우저에 붙여 넣어 참가까지 완료할 수 있다.

## UX-03. AI GM 빠른 시작과 이어하기

### 사용자 결과

- 처음 온 사용자는 캐릭터 규칙을 모두 몰라도 준비된 캐릭터와 입문 시나리오로 바로 시작한다.
- 홈에는 `이어하기`가 가장 먼저 보이고, 현재 장면·마지막 활동·다음 일정이 함께 표시된다.
- 온보딩은 강제 장문 튜토리얼이 아니라 실제 플레이 안에서 필요한 순간에만 나타난다.

### 구현 작업

1. 빠른 시작 오케스트레이션
   - 신규 후보 `POST /sessions/quickstart`를 idempotent하게 구현한다.
   - 검증된 프리셋 캐릭터 생성 또는 재사용, 비공개 1인 AI GM 세션 생성, 캐릭터 연결을 하나의 서비스 흐름으로 묶는다.
   - 일부 단계가 실패하면 고아 세션·고아 캐릭터가 남지 않게 transaction 경계를 정의한다.
2. 온보딩 진행 상태
   - 신규 후보 `UserProductProgress`에 `onboardingVersion`, `quickstartStartedAt`, `firstActionAt`, `completedAt`, `dismissedCoachmarks`를 저장한다.
   - 브라우저 저장소는 화면 표시 캐시로만 쓰고 서버 값을 기준으로 한다.
3. `fe/src/pages/LobbyPage.tsx`
   - 진행 중 세션이 있으면 최근 활동 기준 `이어하기` 카드를 첫 행동으로 배치한다.
   - 세션이 없으면 `AI GM으로 10분 체험`과 `세션 찾기`를 나란히 제공한다.
   - 게스트에게는 시작 전에 7일 보존 정책과 회원 전환 이점을 짧게 알린다.
4. `fe/src/pages/PlayPage.tsx`
   - 첫 플레이에서 세 코치마크만 제공한다: 행동/채팅 구분, 판정 결과 읽기, `/힌트`·`/요약` 사용.
   - 코치마크는 닫기·건너뛰기가 가능하고 다음 방문에 반복하지 않는다.
   - 첫 의미 있는 행동 성공 후 계정 전환 CTA를 방해되지 않는 위치에 표시한다.

### 실패 처리

- 빠른 시작 중 중복 클릭은 같은 idempotency key에 같은 결과를 반환한다.
- AI 호출이 실패해도 세션과 캐릭터는 유지하고 규칙 기반 fallback 또는 재시도 선택을 제공한다.
- 저장된 이어하기 대상이 완료·해산됐으면 활성 목록에서 제거하고 완료 기록으로 안내한다.

### 완료 조건

- 신규 게스트가 첫 화면에서 첫 행동 결과를 보기까지 핵심 클릭이 5회 이내다.
- 같은 빠른 시작 요청을 재전송해도 세션과 캐릭터가 중복 생성되지 않는다.
- 새로고침 또는 다른 기기 로그인 후 홈에서 활성 세션을 다시 열 수 있다.
- 코치마크를 건너뛴 사용자는 다시 강제로 보지 않는다.

## UX-04. 실제 메타데이터와 카탈로그 큐레이션

### 사용자 결과

- 사용자는 실제 예상 시간, 권장 레벨, GM 지원 범위, 테마 태그, 콘텐츠 경고를 보고 시나리오를 고른다.
- 개발용·스모크 테스트용 시나리오는 일반 제공 목록에 보이지 않는다.
- 각 제공 시나리오는 구분 가능한 제목·설명·썸네일을 가진다.

### 구현 작업

1. `ScenarioPublication` 정규화
   - `estimatedMinutes`, `contentWarnings`, `recommendedPlayersMin`, `recommendedPlayersMax` 컬럼 추가를 검토한다.
   - 기존 `tags`, `gmMode`와 함께 공개 메타데이터의 단일 원천으로 사용한다.
   - 기존 attribution의 `P5_PUBLIC_META`는 전환 기간의 backfill 입력으로만 사용한다.
2. `shared-types/src/dto/api/scenarios.dto.ts`
   - 생성/수정 또는 공개 DTO에 공개 메타데이터 필드를 명시한다.
   - 시간·인원·태그 길이와 허용 범위를 검증한다.
   - `ScenarioSummaryResponseDto`를 세션 목록·상세에서 그대로 사용할 수 있게 유지한다.
3. `fe/src/components/SessionDetailModal.tsx`
   - `getDurationLabel`, `getThemeLabel`, `getRecommendationTags`의 제목 추측을 제거한다.
   - 값이 없으면 거짓 fallback 대신 `예상 시간 미정`처럼 명확히 표시한다.
4. `fe/src/data/sessionVisuals.ts`
   - 기본 fallback 한 장을 모든 시나리오의 실제 대표 이미지처럼 반복하지 않는다.
   - 이미지가 없을 때만 중립 placeholder를 사용하고 테마·난이도 데이터는 생성하지 않는다.
5. 제공 시나리오 분리
   - `be/src/modules/scenarios/provided-scenario.constants.ts`에서 사용자 제공용 ID와 내부 검증용 ID를 분리한다.
   - `세션 노드 화면 테스트`, `SRD 5e 룰 런타임 스모크 테스트`는 공개 publication에서 제외한다.
   - 제공 콘텐츠 seed가 공개 대상 목록을 명시적으로 검증한다.
6. backfill
   - `scripts/backfill-scenario-publication.mjs`에 신규 필드 dry-run count와 parse 실패 표본을 추가한다.
   - 구조화 컬럼 read 전 기존 공개 시나리오의 coverage를 100%로 만든다.

### 완료 조건

- 한글 제목을 가진 시나리오도 제목 문자열과 무관하게 저장된 메타데이터를 표시한다.
- 콘텐츠 경고가 목록 미리보기, 세션 상세, 참가 확인에 같은 값으로 나온다.
- 내부 테스트 시나리오가 일반 사용자의 생성·탐색 목록에 0건 노출된다.
- 메타데이터 backfill 두 번째 apply 대상이 0건이다.
- 실제 썸네일이 없는 시나리오를 다른 시나리오의 이미지로 오인시키지 않는다.

## UX-05. 공개 플레이 안전과 운영

### 사용자 결과

- 참가 전에 민감한 소재와 그룹 안전 규칙을 확인한다.
- 플레이 중 누구나 즉시 `잠시 멈춤`, `장면 전환`, `확인 요청` 안전 신호를 보낼 수 있다.
- 사용자는 참가자나 관련 로그를 신고·차단·음소거할 수 있고, 호스트/GM은 권한에 따라 음소거·퇴장 처리한다.

### 데이터 모델 후보

- `SessionSafetyProfile`
  - 세션별 콘텐츠 경고, lines/veils 합의, 안전 신호 사용 여부, 갱신 시각.
- `SessionSafetyPreference`
  - 참가자가 제출한 line/veil 제안. 다른 참가자용 응답에서는 제출자 정보를 제거한다.
- `SessionSafetySignal`
  - `PAUSE`, `FADE_TO_BLACK`, `CHECK_IN`, 상태, 생성·해결 시각, 서버 내부 생성자.
- `UserBlock`
  - 차단자/대상 복합 unique와 생성 시각.
- `SessionUserReport`
  - 신고자, 대상 사용자, 세션, 선택적 `turnLogId`, 이유 코드, 설명, 처리 상태.
- `SessionModerationAction`
  - `MUTE`, `UNMUTE`, `KICK`, `BAN_FROM_SESSION`, 수행자, 대상, 이유, 만료 시각, 감사 기록.

자유 입력 안전 선호와 신고 설명은 일반 참가자 응답이나 계측 로그에 포함하지 않는다. peer에게는 안전 신호 생성자를 익명으로 보여 주되 서버 운영 감사에는 인증 사용자를 보존한다.

### API와 런타임 작업

1. 세션 생성/수정
   - 시나리오 콘텐츠 경고를 기본값으로 복사하고 호스트가 추가 경고와 그룹 합의를 설정한다.
2. 참가 미리보기
   - 경고 확인 checkbox를 단순 면책 문구가 아니라 실제 참가 전 확인 단계로 둔다.
3. 안전 신호
   - 신규 후보 `POST /sessions/:id/safety/signals`와 `POST /sessions/:id/safety/signals/:signalId/resolve`를 추가한다.
   - 활성 신호가 생기면 플레이 행동 입력을 일시 중지한다.
   - Human GM에는 해결 패널을, AI GM에는 `다르게 표현`, `장면 건너뛰기`, `세션 종료` 선택을 보여 준다.
   - AI 요청 중 신호가 발생하면 safety revision이 달라진 늦은 AI 응답을 폐기한다.
4. 신고·차단
   - 참가자 메뉴와 로그 메뉴에서 신고를 시작할 수 있게 한다.
   - 신고 완료와 차단/음소거는 독립 동작으로 제공한다.
   - 차단 관계가 있는 사용자의 공개 모집 세션은 탐색에서 숨기고 신규 공동 참가를 서버 정책에서 차단한다.
5. 음소거·퇴장
   - 개인 음소거는 해당 사용자의 채팅/NPC 자유 발화 표시를 가리되 게임 판정에 필요한 시스템 로그는 유지한다.
   - 세션 음소거와 퇴장은 호스트/GM 권한을 서버에서 검증한다.
   - 기존 `ParticipantStatus.KICKED`를 실제 퇴장 API와 재참가 금지 정책에 연결한다.
6. 운영자 검토
   - 시나리오 moderation과 사람 신고 moderation을 같은 개념으로 혼합하지 않는다.
   - 관리자 화면은 신고 본문과 관련 로그를 최소 권한으로 조회하고 모든 조치를 감사 기록으로 남긴다.

### 실패 처리와 보안

- 신고 API는 대상에게 신고자나 신고 여부를 알리지 않는다.
- 사용자가 자기 자신을 차단·신고하거나 권한 없는 사람이 퇴장시키는 요청은 거절한다.
- 퇴장과 참가가 동시에 발생해도 transaction과 unique 제약으로 최종 상태가 하나만 남는다.
- 차단 사용자가 기존 초대 코드로 재참가하지 못하도록 join policy에서 검사한다.
- 안전 신호 전송 실패 시 로컬에서 멈춘 것처럼 가장하지 않고 재시도와 즉시 세션 나가기 선택을 제공한다.

### 완료 조건

- 콘텐츠 경고가 있는 세션은 경고를 확인하지 않고 참가 확정 단계로 넘어갈 수 없다.
- AI 응답 대기 중 안전 신호를 보내면 늦은 응답이 로그나 상태에 반영되지 않는다.
- 신고, 개인 음소거, 차단, GM 음소거, 퇴장이 서로 다른 권한과 결과로 동작한다.
- 퇴장된 사용자는 초대 코드와 공개 참가 양쪽으로 재입장할 수 없다.
- 차단·신고·안전 선호의 민감한 본문이 일반 로그와 분석 이벤트에 남지 않는다.

## UX-06. 다중 캠페인과 세션 전환

### 사용자 결과

- 사용자는 여러 주간 캠페인에 참여하고, 한 캠페인의 플레이어이면서 다른 캠페인의 호스트가 될 수 있다.
- 홈과 내 세션에서 각 캠페인의 상태·역할·다음 일정·마지막 활동을 비교해 선택한다.

### 구현 작업

1. 전역 차단 제거
   - `isBlockingSessionStatus()`를 create/join의 전역 금지 조건으로 사용하지 않는다.
   - 중복 참가, 정원, 세션 상태는 백엔드의 대상 세션 정책만 판단한다.
2. 활성 세션 상태 분리
   - `useSession.ts`의 단일 스냅샷은 `현재 화면에서 열린 세션` 의미로 제한한다.
   - membership 목록과 현재 실시간 snapshot을 별도 상태로 둔다.
   - route의 session public ID를 현재 세션의 단일 원천으로 삼는다.
3. Socket 전환
   - 세션 이동 시 이전 room leave 확인 후 새 room join을 수행한다.
   - 이전 세션의 늦은 이벤트는 session ID가 현재 route와 다르면 적용하지 않는다.
4. 홈과 프로필
   - `LobbyPage`에 활성 캠페인 목록과 이어하기를 추가한다.
   - `ProfilePage`의 최근 세션 행을 권한 있는 세션 상세로 연결한다.
   - 완료/해산 세션은 활성 목록과 기록 목록을 구분한다.
5. 사용자 메시지
   - `모집 중인 세션에는 하나만 참여` 문구를 제거한다.
   - 실제 실패 이유인 정원, 상태, 차단 관계, 이미 참여 중을 구분해 안내한다.

### 완료 조건

- 한 사용자가 동시에 두 모집/진행 세션의 구성원이 될 수 있다.
- 한 세션을 열어 둔 상태에서 다른 세션을 열면 이전 세션 이벤트가 현재 화면에 섞이지 않는다.
- 다른 세션 참가가 기존 저장 snapshot을 삭제하지 않는다.
- 완료 세션은 이어하기에 나오지 않지만 기록에서 열 수 있다.

## UX-07. AI 신뢰와 턴 제어

### P0 범위

1. AI GM 시작 전 고지
   - 외부 AI 제공자 사용 여부.
   - 행동 원문, 필요한 세션 상태, 최근 로그 일부, 필요한 룰 조각이 전송될 수 있다는 범주 설명.
   - 30초 응답 목표와 실패 시 fallback 존재.
   - 데이터 보존 기간과 삭제 정책 링크.
2. 실제 처리 단계
   - `해석 중`, `규칙 확인 중`, `서술 생성 중`을 서버 이벤트가 보장할 때만 표시한다.
   - 단순 시간 기반 가짜 진행률은 사용하지 않는다.
3. 취소
   - 상태 적용 전에는 요청 취소를 허용한다.
   - 서버는 request ID와 cancellation state를 확인해 늦은 결과를 폐기한다.

AI 데이터 보존 기간과 Google 측 보존 조건은 현재 제품 문서만으로 사용자용 확정 문구를 만들 수 없다. 공개 베타 전에 정책을 확정하고 신규 기준 문서 `doc/rules/AI_DATA_HANDLING_RULES.md`에 기록해야 한다.

### P1 범위

1. 안전한 재시도
   - 상태 변경 전 실패는 같은 의도와 idempotency key로 재시도한다.
   - 상태 변경 후에는 판정이나 피해를 다시 적용하지 않고 서술만 재생성한다.
2. 해석 피드백
   - `의도와 달라요`는 원문을 다시 공개 로그에 쓰지 않고 수정 입력 흐름을 연다.
   - 이미 확정된 상태를 자동 rollback하지 않는다.
3. 품질 피드백
   - `도움됨/도움 안 됨`과 이유 코드를 `AiTurnFeedback`에 저장한다.
   - 프롬프트나 전체 로그를 분석 이벤트에 복제하지 않는다.
4. 평가 하네스
   - `doc/PENDING_WORK_ITEMS.md`의 AI 품질 평가 작업과 연결해 해석 정확도, validator 실패율, fallback 비율, 취소 후 상태 변경 0건을 측정한다.

### 완료 조건

- 처리 단계 UI와 실제 서버 단계가 일치한다.
- 취소 성공 뒤 해당 AI 요청으로 생성된 로그·판정·상태 변경이 0건이다.
- 서술 재생성이 주사위, HP, 자원, 인벤토리를 다시 변경하지 않는다.
- 첫 AI GM 진입 전에 데이터 범주와 정책을 확인할 수 있다.

## UX-08. 시나리오 제작자와 사람 GM 흐름

### 사용자 결과

- 비개발자 GM이 raw ID, flag key, enum을 몰라도 짧은 시나리오를 만들고 검증·공개한다.
- 고급 사용자는 기존 편집 기능을 잃지 않고 명시적인 고급 모드에서 사용한다.
- 사람 GM은 플레이 중 자주 쓰는 진행 작업을 적은 클릭으로 실행한다.

### 구현 작업

1. 편집 모드 분리
   - 기본 모드: 기본 정보 → 공개 메타데이터 → 장면 → NPC/단서 → 판정/전환 → 미리보기 → 공개.
   - 고급 모드: 기존 상세 node/meta/flag 기능을 유지하되 개발자 용어임을 명시한다.
2. `fe/src/pages/ScenarioEditorPage.tsx`
   - 4천 줄 규모 페이지를 단계별 section/component와 form state hook으로 분리한다.
   - `window.prompt`, `window.confirm`을 검증 가능한 dialog form으로 교체한다.
   - 공개 범위, 변경 요약, 권리 확인, fork 허용을 한 공개 dialog에서 받는다.
3. 사용자용 선택지
   - `AUTO_REVEAL`, flag key, node ID를 직접 입력시키는 대신 사용자 설명이 있는 select/template을 제공한다.
   - 고급 raw 입력은 기본 모드에서 숨긴다.
4. 검증
   - 공개 전 오류는 node ID가 아니라 장면 제목과 수정 링크로 표시한다.
   - 콘텐츠 경고, 예상 시간, 권장 인원 누락은 공개 전 확인 대상으로 둔다.
5. 사람 GM 패널
   - 메시지, NPC 발화, 장면 전환, 자료 공개, 전투 시작, 안전 신호 해결을 1차 행동으로 묶는다.
   - 캠페인 완결·보관 화면의 `P6`, archive ID, current node ID를 사용자 용어로 바꾼다.

### 완료 조건

- 기본 모드에서 내부 ID나 flag key를 직접 입력하지 않고 최소 3장면 시나리오를 공개할 수 있다.
- 공개 dialog를 취소해도 draft가 손상되지 않는다.
- validation 오류에서 해당 장면 편집 위치로 바로 이동한다.
- 사람 GM이 현재 장면을 확인한 상태에서 주요 운영 행동을 두 번 이내의 조작으로 실행한다.

## UX-09. 사용자용 언어와 완성된 표면

### 구현 작업

1. 표시 계층
   - `fe/src/presentation` 후보 디렉터리에 세션 상태, 단계, 공개 범위, GM 모드, 참가자 역할의 exhaustive label map을 둔다.
   - 서버 raw error message 대신 API error code를 사용자 문구로 변환한다.
2. 내부 값 제거
   - 계정의 user ID, 레벨업 미리보기의 session/node ID, 세션 보관 화면의 archive/node ID를 일반 화면에서 제거한다.
   - 필요한 진단 값은 개발자 모드와 구조화 로그로만 이동한다.
3. 미완성 화면
   - 실제 설정이 하나도 없는 동안 `/settings` 메뉴와 `Coming soon` 화면을 숨긴다.
   - 공개 프로필의 미래 기능 설명 카드는 구현된 정보 중심 화면으로 교체한다.
4. 정적 gate
   - 신규 후보 `scripts/verify-user-facing-identifiers.mjs`에서 JSX의 직접 `.id`, `*Id`, raw enum 렌더링 패턴을 allowlist 기반으로 점검한다.
   - false positive가 많은 범용 검색 대신 실제 렌더링 표현식을 우선 검사한다.

### 완료 조건

- 일반 사용자 화면에서 cuid/UUID/catalog key/raw enum을 찾을 수 없다.
- 서버 영문 오류가 toast나 본문에 그대로 노출되지 않는다.
- 존재하지 않는 기능을 메뉴의 주요 행동으로 안내하지 않는다.
- 새 enum 값 추가 시 사용자 label 누락이 타입 검사에서 드러난다.

## UX-10. 접근성과 모바일 웹

### 공개 베타 차단 범위

- 로그인, 홈, 세션 탐색, 생성, 초대 참가, 캐릭터 선택, 기본 행동 입력을 키보드만으로 완료한다.
- dialog는 초점 진입, Tab 순환, Escape 닫기, 닫은 뒤 초점 복귀를 지원한다.
- `article role="button"` 같은 가짜 버튼은 실제 `button` 또는 `a`로 교체한다.
- 오류·선택·상태를 색상만으로 전달하지 않는다.
- 200% 확대와 360px 폭에서 가로 스크롤 없이 핵심 흐름을 완료한다.

### P1 확장 범위

1. 모바일 플레이 레이아웃
   - 단순 세로 적층 대신 `메인`, `캐릭터`, `자료`, `채팅` 탭을 적용한다.
   - 행동 입력과 현재 결과는 어느 탭에서도 접근 가능한 고정 우선 영역으로 둔다.
2. VTT 대체 조작
   - drag 전용 토큰 이동에 토큰 선택 + 방향/거리 입력 또는 키보드 이동 패널을 추가한다.
   - 맵을 사용하지 못해도 텍스트 행동 입력으로 같은 핵심 게임 행동을 수행할 수 있게 한다.
3. 시각·운동
   - WCAG 2.2 AA 대비, 44px 터치 영역, `prefers-reduced-motion`, 스크린 리더용 live region을 적용한다.
4. 자동 검증 기반
   - FE에 Vitest, React Testing Library, axe 기반 검사와 최소 Playwright 접근성 smoke 흐름을 추가한다.
   - `fe/package.json`에 test script를 명시한다.

### 완료 조건

- 키보드만으로 공개 세션을 찾아 참가하고 첫 행동을 전송할 수 있다.
- VTT 토큰을 drag하지 않고도 이동 요청을 만들 수 있다.
- 모바일 탭 전환이 플레이 상태나 작성 중 입력을 잃지 않는다.
- 핵심 화면 axe 자동 검사에서 serious/critical 위반이 0건이다.

## UX-11. 계정과 사전 조율

### P0 범위

1. OAuth 계정 탈퇴
   - 로컬 계정은 현재 비밀번호를 확인한다.
   - Kakao/Discord 계정은 짧은 수명의 provider 재인증 ticket을 확인한다.
   - 게스트는 비밀번호 대신 명시적 최종 확인을 사용한다.
   - `canDeleteAccount`는 provider별 실제 가능한 흐름과 일치해야 한다.
2. 게스트 보존 안내
   - 게스트 로그인 버튼 근처, 빠른 시작 전, 계정 화면에 7일 보존 정책을 일관되게 표시한다.
   - 회원 전환 전 어떤 캐릭터와 세션이 유지되는지 설명한다.

### P1 범위

1. 비밀번호 관리
   - `PATCH /users/me/password`로 로그인 상태 변경을 지원한다.
   - reset token은 hash 저장, 짧은 만료, 1회 사용으로 구현한다.
   - 존재하지 않는 이메일도 요청 응답은 동일하게 반환한다.
2. 이메일 확인과 복구
   - 이메일 발송 provider interface와 실패 재시도 정책을 정의한다.
   - 발송 서비스가 결정되기 전 공개 가입의 복구 가능성을 완료로 판정하지 않는다.
3. 프로필 기반 조율
   - 선택형 경험 수준, 선호 역할, GM/플레이 스타일, 시간대, 일정 요약을 추가한다.
   - 공개 범위는 항목별 opt-in으로 둔다.
   - 활성 비공개 세션이나 상세 플레이 이력은 공개 프로필에 노출하지 않는다.
4. 참가 메모
   - 세션 참가 전 호스트에게 전달할 짧은 신청 메모를 지원하되 자유 형식 DM으로 확장하지 않는다.

### 완료 조건

- LOCAL, KAKAO, DISCORD, GUEST 계정이 각각 맞는 확인 방식으로 탈퇴를 완료할 수 있다.
- 비밀번호 재설정 token 재사용과 만료 후 사용이 거절된다.
- 공개 프로필의 일정·선호 정보는 사용자가 공개한 항목만 보인다.
- 게스트가 데이터 보존 기간을 알지 못한 채 빠른 시작을 완료하지 않는다.

- 기능별 자동 테스트 결과와 수동 여정 결과를 별도 dev-note에 기록한다.
- 실패 스크린샷, API error code, 재현 계정 역할, 세션 상태를 함께 기록하되 민감한 본문은 제거한다.
- P0 완료 체크박스는 코드 작성만으로 닫지 않고 사용자 여정 검증 증거가 있을 때만 닫는다.

## 8. 데이터 전환 계획

### migration이 필요한 작업

- 시나리오 공개 메타데이터 정규화
- 온보딩 진행 상태
- 세션 안전 프로필·신호·선호
- 사용자 차단·신고·세션 moderation action
- AI 턴 피드백
- 비밀번호 reset token 또는 인증 challenge

### 전환 원칙

- 모든 backfill은 기본 dry-run이며 명시적인 apply에서만 쓴다.
- 시나리오 메타데이터는 구조화 컬럼 coverage가 100%가 되기 전 read source를 전환하지 않는다.
- 신규 안전/차단 테이블은 빈 상태에서 시작하며 기존 로그로 사용자 관계를 추론하지 않는다.
- 계정 provider에 따른 탈퇴 가능 여부를 backfill로 임의 변경하지 않는다.
- migration과 backfill 적용은 이 계획의 문서 작성 범위에 포함하지 않는다.

## 9. 공통 완료 정의

각 작업은 다음을 모두 만족해야 완료다.

- shared DTO, decoder, FE type, BE validation이 같은 계약을 사용한다.
- 권한 없는 요청, 중복 요청, 오래된 응답, 빈 결과, 네트워크 실패를 처리한다.
- loading, empty, error, disabled 상태가 사용자 문구로 구분된다.
- 사용자 화면에 내부 ID와 raw enum이 노출되지 않는다.
- 키보드 접근, focus 관리, 모바일 핵심 흐름을 확인한다.
- 민감한 원문을 로그·분석 이벤트에 추가하지 않는다.
- 필요한 migration은 dry-run과 재실행 멱등성을 확인한다.
- 자동 검증 코드와 수동 검증 시나리오를 함께 추가한다.
- `structure/SCREEN.md`, `structure/QUALITY_MVP_ACCEPTANCE.md` 등 기준 문서를 실제 구현과 맞춘다.
- 사용자가 테스트를 실행하고 결과를 기록하기 전에는 `동적 검증 완료`로 표시하지 않는다.

## 10. 사용자 검증 계획

프로젝트 규칙에 따라 이 문서 작성 과정에서는 테스트를 실행하지 않았다. 구현 후 사용자가 변경 범위에 맞춰 다음 검증을 직접 실행한다.

### 현재 존재하는 명령

```powershell
npm run build -w @trpg/shared-types
npm run build -w @trpg/be
npm run build -w @trpg/fe
npm run test:e2e
npm run test:p6-regression
npm run eval:ai-quality
```

### 구현 과정에서 추가할 명령

아래 스크립트는 현재 `fe/package.json`에 없으므로 테스트 기반을 구현한 뒤 추가한다.

```powershell
npm run test -w @trpg/fe
npm run test:a11y -w @trpg/fe
npm run test:ux-e2e
npm run verify:user-facing-identifiers
```

### 필수 수동 여정

1. 공개 세션을 12개 이상 준비하고 11번째 세션을 검색·필터·페이지 이동으로 연다.
2. 공개/비공개 세션을 만들고 설명·일정·총 인원을 수정한 뒤 새 브라우저에서 초대 링크로 참가한다.
3. 신규 게스트가 빠른 시작 → 프리셋 캐릭터 → 첫 AI GM 행동 → `/힌트` → `/요약`을 완료한다.
4. 로그아웃·로그인 또는 다른 브라우저에서 같은 캠페인을 홈 `이어하기`로 재개한다.
5. 한 계정이 두 캠페인에 참여하고 두 세션 사이를 전환해 이벤트가 섞이지 않는지 확인한다.
6. 콘텐츠 경고 확인, 안전 신호, 개인 음소거, 신고, 차단, GM 퇴장을 역할별 계정으로 확인한다.
7. AI 응답 중 취소·안전 신호를 보내고 늦은 응답이 상태를 변경하지 않는지 확인한다.
8. LOCAL/KAKAO/DISCORD/GUEST 계정 탈퇴와 비밀번호 복구를 provider별로 확인한다.
9. 마우스 없이 로그인 → 세션 검색 → 참가 → 캐릭터 선택 → 첫 행동을 완료한다.
10. 360px 모바일 뷰와 200% 확대에서 플레이 탭, 행동 입력, 안전 신호를 사용할 수 있는지 확인한다.

## 11. 공개 베타 판정

다음 조건 중 하나라도 충족하지 못하면 공개 베타 대신 초대형 비공개 알파를 유지한다.

- [ ] 공개/내 세션 목록이 10건을 넘어도 누락되지 않는다.
- [ ] 세션 생성·수정·비공개 초대 링크가 처음부터 끝까지 동작한다.
- [ ] 신규 사용자가 빠른 시작으로 첫 AI 행동을 완료하고 재방문해 이어서 플레이한다.
- [ ] 시나리오 상세가 실제 메타데이터만 표시하고 내부 테스트 콘텐츠를 숨긴다.
- [ ] 콘텐츠 경고, 안전 신호, 신고·차단·음소거·퇴장이 동작한다.
- [ ] AI 데이터 이용 고지와 취소 후 상태 불변 계약이 확인된다.
- [ ] 일반 사용자 화면의 내부 ID/raw enum과 준비 중 주요 메뉴가 제거된다.
- [ ] OAuth 포함 모든 계정 유형이 탈퇴할 수 있고 게스트 보존 정책이 사전 고지된다.
- [ ] 키보드로 로그인부터 첫 행동까지 완료할 수 있다.
- [ ] 핵심 자동 회귀, E2E, AI 평가, 수동 사용자 여정의 검증 증거가 기록되어 있다.

## 12. 구현 전 확정이 필요한 외부 결정

두 항목은 코드만으로 정답을 만들 수 없어 담당자의 제품·운영 결정이 필요하다.

1. AI 데이터 보존 정책
   - 앱 서버의 프롬프트/응답 보존 기간, 사용자 삭제 범위, Google AI Studio 측 데이터 처리 조건을 확정해야 한다.
2. 이메일 발송 제공자
   - 비밀번호 재설정과 이메일 확인을 실제로 전달할 provider, 발송 실패·재시도·rate limit 정책을 정해야 한다.

두 결정이 나기 전에도 인터페이스와 로컬 stub은 만들 수 있지만, 사용자에게 복구와 데이터 보존을 완료 기능처럼 안내해서는 안 된다.
